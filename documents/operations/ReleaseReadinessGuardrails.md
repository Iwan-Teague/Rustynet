# Release Readiness Guardrails

## Purpose

Define the one durable sign-off path for Rustynet release readiness.

This guardrail is intentionally stricter than the reduced helper workflow. It is
the operator and CI entrypoint that keeps the critical Rust, advisory, license,
and live-lab evidence gates together instead of relying on ad hoc judgment.

## Primary Command

Run:

```bash
./scripts/ci/release_readiness_gates.sh
```

That wrapper executes:

1. `./scripts/ci/phase5_gates.sh`
2. `./scripts/ci/phase10_gates.sh`

The result is fail-closed:

- Rust formatting, clippy, check, and test gates must pass.
- Phase 5 release-doc/provenance/SBOM gates must pass.
- Advisory and license policy gates must pass.
- Fresh-install release-gate evidence must validate.
- Canonical Phase 10 cross-network evidence must validate.
- The final readiness docs and bundle manifest must exist.

If any one of those inputs is missing, stale, malformed, or not bound to the
current commit/evidence state, the release-readiness gate must fail.

## Release Workflow Wiring

`.github/workflows/release.yml` runs `./scripts/ci/release_readiness_gates.sh`
in its `release_gates` job. The `build` job needs `release_gates` and the
`manifest` (sign + publish) job needs `build`, so on a pushed `v*.*.*` tag a
failing or missing readiness gate stops the binaries, the signed manifest and
the GitHub Release upload. There is no skip or soft-fail path on the tag push.

- Manual `workflow_dispatch` runs are dry-runs that never publish; for those the
  job is `continue-on-error` so the build/manifest mechanics can still be
  checked, and the gate failure is still shown on the run.
- The gate's evidence inputs (`artifacts/phase10/fresh_install_os_matrix_report.json`,
  the cross-network reports) live under the gitignored `artifacts/` tree. They
  must be present on the runner for the gate to pass; until the commit-bound
  evidence is produced (TODO V14, V18) and delivered to the runner, a tag push
  fails at `release_gates` by design.
- The `phase5_gate_report.json` and `phase5_readiness_bundle.json` the run
  regenerates are uploaded as the `release-readiness-reports` workflow
  artifact, including when the gate fails.
- The `release_workflow_wires_the_readiness_gate` and
  `release_workflow_wiring_check_rejects_weakened_workflows` tests in
  `crates/rustynet-cli/src/bin/release_readiness_gates.rs` fail if the gate is
  removed, softened (`|| true`, tag-push `continue-on-error`, a skipping `if:`)
  or no longer upstream of the publish job.

## Authoritative Reporting

The gate reports are generated by the gate commands themselves on every run:

- `artifacts/release/phase5_gate_report.json`
- `artifacts/release/phase5_readiness_bundle.json`

Those reports must distinguish:

- `executed_passed`
- `executed_failed`
- `not_executed`

Pre-existing files are not proof. A stale bundle file or report file must not be
treated as release evidence unless the current gate execution regenerated it and
its required steps are recorded as `executed_passed`.

`cargo audit --deny warnings` and `cargo deny check advisories bans licenses
sources` are Phase 5 hard gates. If either command is absent or fails, the
Phase 5 gate and the top-level release-readiness gate must fail with a non-zero
exit status.

## Evidence Boundaries

Reduced helper evidence is useful for narrowing runtime defects, but it is not a
substitute for full release-gate evidence.

The release-ready claim requires:

- current Phase 5 docs and final bundle
- current fresh-install OS matrix evidence for the exact commit under test
- current canonical cross-network evidence for the exact commit under test

Reduced helper or same-underlay local-lab reruns must not be presented as if
they satisfy the full release-gate path.

## Operator Security Preconditions

The release-readiness and live-lab automation path assumes all of the following:

- SSH host trust is pinned
  - use a pinned `known_hosts` file
  - no TOFU / `accept-new` in automation
- SSH authentication uses operator key material with owner-only permissions
- passwordless sudo is available on automation targets
  - `sudo -n` must succeed
  - password-file based sudo is not part of the active live-lab wrapper path
- secret custody for unattended runtime remains credential-only
  - encrypted systemd credentials
  - no plaintext runtime passphrase files at rest

If any of those expectations are not true, stop before claiming release
evidence.
