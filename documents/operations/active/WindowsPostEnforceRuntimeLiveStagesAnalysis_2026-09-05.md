## 1) Symptom / question

`enforce_baseline_runtime` was fixed (`3f7fc8d3`): the daemon now applies the tunnel-interface WFP permit (`DataplaneSystem::apply_tunnel_interface_admit`, a new non-defaulted trait method) immediately after `backend.start()` creates the WireGuard-NT adapter, instead of inside the pre-start `apply_firewall_killswitch` where `ConvertInterfaceAliasToLuid(rustynet0)` always failed with ERROR_INVALID_PARAMETER (87) on a cold bootstrap. The question this document answers, in three parts: **(1)** what `validate_baseline_runtime` actually validates on Windows and what can still be wrong even after the daemon-start problem is fixed; **(2)** whether any OTHER Windows path carries the same "operation requires the tunnel interface to already exist" ordering precondition that `3f7fc8d3` fixed; **(3)** what each live-validation stage requires of a Windows node, and which stages have Windows gates, Windows-agnostic adapter dispatch, or hardcoded non-Windows assumptions.

## 3) `validate_baseline_runtime` on Windows

### 3.1 Orchestrator side

`ValidateBaselineRuntimeStage` (`orchestrator/stage/validate_runtime.rs`): deps `[EnforceBaselineRuntime]` (:141-143); PerNode over **every** assignment; `applies_to_roles` empty (all roles, :144-146). For each node it dispatches SIX daemon probes (:150-157): `RuntimeAcls`, `ServiceHardening`, `KeyCustody`, `Authenticode`, `MeshStatus`, `DnsFailclosed`, via `adapter.run_validator(op, probe_expectations(op))` (:166-172).

- `probe_expectations` (:63-70) emits `--max-age-seconds <SNAPSHOT_MAX_AGE_SECONDS>` (180, shared with `mesh_status_validation`, `role_validation/mesh_status.rs`) for `MeshStatus` only. QH-39 doc (:33-62): without expectations, `windows_mesh_status.rs` nests both staleness and future-timestamp tests inside `if let Some(max_age)`, so an expectation-less mesh-status asserts nothing. `--expected-peer-id` is deliberately NOT emitted: the daemon persists `SessionStateSnapshot.peer_ids` from *advertised route CIDRs*, not peer node ids (`daemon.rs:9762-9765`), so asserting node ids would red every node (a named, separate daemon-side defect).
- The Windows probe argv (`vm_lab/mod.rs:10300-10327`, `WindowsDaemonProbe::build_argv`) is `<rustynetd.exe> windows-{runtime-acls,service-hardening,key-custody,authenticode,mesh-status,dns-failclosed}-check --no-fail-on-drift` — always with `--no-fail-on-drift`.
- `run_validator` (`orchestrator/adapter/windows.rs:197-223`) renders the argv into a PowerShell script, runs it, and judges the output with `validator_report_ok` (`orchestrator/adapter/ssh.rs:919-951`): **the verdict is `overall_ok`-and-`drift_reasons`-based, not exit-code based** — `overall_ok: false` OR any non-empty `drift_reasons` array fails the op; a report with neither field is skipped; no parseable report at all fails closed (`saw_ok=false`). The `--no-fail-on-drift` flag only stops the daemon process from exiting non-zero; the orchestrator still fails on drift. Evidence (daemon report verbatim) lands in `validator_results.json` and `logs/validate_baseline_runtime.validator-evidence.json` (:239-260).

So `validate_baseline_runtime` on Windows checks exactly what those six daemon subcommands report. It does **not** ping the mesh IP, does **not** check routes, and does **not** run the orchestrator-side killswitch probe — the closest things are the daemon's own state-file and posture reports below.

Net: even with `3f7fc8d3` working, `validate_baseline_runtime` has two structurally-likely Windows failures — `Authenticode` (unsigned lab build) and `DnsFailclosed` (physical-NIC DHCP DNS) — unless the lab path does something this trace did not find (e.g. a guest-local test-signing step or a DNS rewrite this trace missed). Both would fail via `drift_reasons`, diagnosable verbatim from `validator_results.json` in the report dir.

### 3.3 What `enforce_baseline_runtime` leaves behind (the precondition this stage inherits)

`enforce_daemon` (`windows_install.rs:521-560`) patches `--auto-tunnel-enforce` into `rustynetd.env`, stop+starts the service, and waits up to 100 s for the adapter to hold an IPv4 address (the wait script also rejects any `*rustynet*`/`*WireGuard*` adapter with a 169.254.* address, :853-865). First daemon start runs the full bootstrap apply (`daemon.rs:8935-8959` → `controller.apply_dataplane_generation`; failures land in `bootstrap_apply_failed` at `daemon.rs:8971/:8979`). The order inside `apply_dataplane_generation` (`phase10.rs:7226+`): `apply_firewall_killswitch` (:7270, pre-start — block-outbound policy, loopback allow, scoped egress allows; the tunnel permit is deliberately NOT here anymore) → `backend.start(context)` (:7278) → `apply_tunnel_interface_admit` (:7295, the `3f7fc8d3` fix) → `admit_host_firewall_forwarding` (:7319, gated, Linux firewalld only) → then `apply_generation_stages` (`phase10.rs:7517+`): rollback_routes → endpoint-bypass routes (:7542-7549) → `apply_routes` (:7556) → `apply_nat_forwarding` (exit roles) → DNS posture (:7582-7589) → IPv6 egress disable → asserts.

## 4) `blind_exit` on Windows

`blind_exit` (Setup/T1Role, `stage/blind_exit.rs`) self-filters: no BlindExit assignment → `Skipped("no node in this topology is assigned the blind_exit role")` (:38-42). With a blind_exit node, the per-node gate is `blind_exit_runtime_implemented` (`role_validation/blind_exit.rs:5-7`) = **Linux | macOS only**; Windows nodes are reported-skipped (stage/blind_exit.rs:55-58), which caps the stage at `Skipped` (:89). The module comment (:13) states the production fact directly: "blind_exit is blocked on Windows in production, but the code path stays correct" (the validator would use `rustynet.exe`). The typical windows-x86-1-as-Exit topology contains no blind_exit node, so expect `Skipped` and a Partial run verdict, not a failure. The dedicated `blind_exit_dataplane_validation` live stage is Linux-only (`role_validation/blind_exit_dataplane.rs:14-16`) → Windows reported-skip.

## 5) Same-bug-class sweep: "needs the tunnel interface to already exist"

The fixed defect's shape: a Windows operation resolves the interface **alias → LUID** (`interface_alias_to_luid`, `rustynet-windows-native/src/lib.rs:1561-1573`, wrapping `ConvertInterfaceAliasToLuid`) or otherwise interface-scopes config, and ran before `backend.start()` created the adapter. Every caller found:

1. **`apply_wfp_tunnel_permit`** (`lib.rs:1656-1690` area, alias→LUID at :1667) — the fixed one; now only called from `WindowsCommandSystem::apply_tunnel_interface_admit` (`phase10.rs:6320-6341`), which the controller invokes at `phase10.rs:7295` strictly after `backend.start()` (:7278). Safe by construction (and deliberately non-defaulted in the trait, `phase10.rs:611-629`, so a missing dispatch arm cannot silently no-op).
2. **`wfp_tunnel_permit_present`** (`lib.rs:1872-1911`, alias→LUID at :1872 plus forbidden-alias resolution :1879) — the `assert_killswitch` read-back (`phase10.rs:6585-6652`, WFP verification at :6626+). Only reached from the assert path, which runs inside `apply_generation_stages` (post-start). Same precondition, correct ordering today — but note it is the same hazard class: if a restart/rollback path ever tore the adapter down without re-running the apply chain, this assert fails with an alias-resolution error, which is the *correct* fail-closed behavior, not a bug.
3. **Windows DNS loopback + NRPT** (`apply_dns_loopback`, `phase10.rs:5855-5884`; `windows_dns_set_args`/`windows_dns_set_ipv6_loopback_args` at :9020-9058; NRPT via `reg.exe add` at :9061-9090 — registry writes, not the WMI-wedging `Add-DnsClientNrptRule` CIM cmdlet, doc :9053-9059) — `netsh interface ... set dnsservers name=rustynet0` needs the interface to exist; reached only via `apply_dns_protection` (:6417-6478) → `apply_generation_stages` :7582-7589, post-start. **Safe by ordering.** (This is where §3.2's *verifier-contract* gap lives — the apply is fine; the check is stricter than the apply.)
4. **Windows `apply_routes` is a no-op** (`phase10.rs:6262-6264`, `Ok(())`): mesh/exit routing on Windows is owned by the WireGuard-NT adapter config, not OS route adds, so the Linux-style "route add before interface exists" hazard has no Windows analog in the route path. `rollback_routes` (:6266-6273) only deletes endpoint-bypass /32s added post-start. Endpoint-bypass routes themselves (`apply_peer_endpoint_bypass_routes` :6237-6260, `add_endpoint_bypass_route` :5926+) target the *underlay* nexthop and do not reference the tunnel interface.
5. **Exit-serving assertions** (`assert_exit_serving` `phase10.rs:6650-6672`: NetNat check + IP-forwarding check by interface alias via `WINDOWS_PS_ASSERT_FORWARDING_ENABLED`) and `apply_nat_forwarding`/`apply_windows_exit_nat_forwarding` — all post-start, exit-roles only. Safe by ordering; they would fail loudly on a vanished adapter.
6. **Orchestrator-side** interface reads are all post-start waits or probes: the adapter-IPv4-within-90 s readiness script (`windows_install.rs:847-865`), the daemon readiness probe (:892-909), `collect_mesh_ip` (comment at :847: fails if read before the IP is assigned — which is why the wait exists). `check_prerequisites` (:6150-6155 in phase10's Windows block) only resolves netsh/PowerShell/reg binaries — no interface dependency.

**Verdict: no second live instance of the bug class was found.** The remaining alias-scoped operations (items 2, 3, 5) all run after `backend.start()` in the single apply chain, and the trait's non-defaulted methods (QH-53/QH-52 style) force every new system type to decide explicitly. The one structural caveat: items 2/3/5 share the fixed bug's *precondition* and are protected only by call-site ordering, not by types — a future refactor that moves any of them before `backend.start()` would reintroduce the failure mode silently.

## 8) Ranked best-guess: what fails first when run-2026-09-05-windows-11 gets past `enforce_baseline_runtime`

Grounded ranking, most → least likely:

1. **`validate_baseline_runtime` fails on `windows-dns-failclosed-check`** — physical-NIC DHCP DNS is non-loopback and the Windows apply path never pins it (`phase10.rs:5855-5884` tunnel-only vs `windows_dns_failclosed.rs:160-165` all-interfaces contract). Fails via `drift_reasons` even with a healthy daemon. The macOS posture (pin every service) shows the intended shape; Windows has no analog.
2. **`validate_baseline_runtime` fails on `windows-authenticode-check`** — the lab-built `rustynetd.exe` is unsigned; `overall_ok` requires `signature_present && chain_verified` (`windows_authenticode.rs:371`). No signing step exists anywhere in `windows_install.rs`.
3. **`authenticode_validation` / `dns_failclosed_validation` (live stages) fail identically** once the Setup-tier stage is (hypothetically) passed or skipped — same checks, dedicated stages; note `validate_baseline_runtime` is T0Core and will skip-cascade nothing, so 1/2 come first.
4. **`role_switch_matrix` fails with "daemon reports no active WireGuard tunnels"** if `wg.exe` is not at the reviewed path on the guest (`windows_traffic.rs:229-245` filters the sentinel into an empty list). Depends on the guest image having WireGuard for Windows installed — a bootstrap prerequisite, not a code path.
5. **`live_managed_dns_validation` fails the run by design** on any Windows-containing topology (`:288-303`). Loud, self-describing, and a real parity gap (POSIX-only bundle reading) rather than a flake.
6. **`traffic_test_matrix` / `active_exit` / `exit_handoff` mesh-level failures** — only if the underlying dataplane (now that WFP permit applies post-start) still doesn't pass traffic: e.g. the scoped egress allow missing a required underlay endpoint, or NAT/forwarding on the Windows exit. These are the stages the fix was *for*, so their failure would be genuine new signal, not ordering debt.
7. Expected non-failures to not misread: `blind_exit` → Skipped (no blind_exit node / Windows blocked by gate), `gossip_convergence_validation` / `ipv6_leak_validation` / `exit_dns_failclosed` / `exit_nat_lifecycle` / `exit_demotion_residue` / `blind_exit_dataplane` → reported-skips on Windows, each capping the run verdict at Partial by design.

## 9) Proposed fixes (NOT implemented — this document changes nothing)

1. **DNS fail-closed contract parity**: either extend `apply_dns_loopback` to pin the underlay interfaces' DNS to loopback (the macOS M1 shape, with backup/rollback), or narrow the Windows evaluator to exempt non-tunnel interfaces whose port-53 egress is firewalled — one of the two must give; today the enforcer and the verifier disagree.
2. **Authenticode in the lab**: sign the lab binary (test certificate + `signtool`/`Set-AuthenticodeSignature` in bootstrap) or add an explicit, loud lab-mode flag to `windows-authenticode-check` (mirroring how Linux reports `applicable: false` honestly) so the control stays real in production but the lab evidence is truthful.
3. **`live_managed_dns_validation`**: platform-dispatch the bundle read (Windows: named-pipe/`rustynet.exe` path or a `windows` arm reading the state root) instead of hard-failing; until then the stage documents itself as the Windows release blocker it is.
4. **Guard the ordering invariant in types where cheap**: items 2/3/5 in §5 are safe only by call-site order; consider a marker/state bit (like `StageMarker::FirewallApplied`) asserting "backend started" before alias-scoped asserts/DNS applies can run.
5. Emit `--expected-peer-id` for mesh-status once the `peer_ids`-from-advertised-routes daemon defect is fixed (`validate_runtime.rs:53-62` documents it), so peer visibility is actually asserted on Windows.
