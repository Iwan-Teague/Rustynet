# Live-Lab Extensibility Assessment — is the `--node` lab modular or bolted on?

**Date:** 2026-09-08 · **Tree:** commit `0e649c65` (worktree, clean) · **Method:** docs-only grounded code-trace; no code changed. Every claim carries `file:line` at this commit. Counts are measured, not estimated. Reference example for "adding a stage" is `refresh_signed_bundles` (the newest stage in the tree, added for the TraversalBundleFreshnessPlan half (a), and the subject of QH-80).

---

## 1) Executive verdict

**The stage axis is genuinely modular — not bolted on. Adding a new stage is a compiler- and test-forced six-touchpoint recipe that is self-documented at the point of use, and the contract (what a stage must declare, what outcomes may exist, what happens on skip) is fail-closed by design.**

**The OS axis is the weak one — this is where the lab is bolted on.** One 53-method adapter trait plus **769 references to `VmGuestPlatform::` outside the adapter layer** mean a new OS compiles fine but behaves silently wrong wherever a stage branches on platform inline.

**The deepest structural gap is not syntax but completeness:** nothing checks that the lab *environment* provides what a stage needs. QH-80 (`QualityHardeningTodo_2026-07-25.md:6678+`) is the proof — `relay_forwards_frame_validation` was wired, catalogued, documented, and yet **unreachable for its entire life** because the lab never minted a relay candidate; discovered on its first-ever execution, 2026-09-08, three months after it was added.

Overall: **modular for stages and validators, tolerable for tests, bolted-on for OS support and un-guardable for environment completeness.** Details and recommendations below.

## 2) The stage recipe, measured

The recipe is written down where you need it: `crates/rustynet-cli/src/vm_lab/orchestrator/plan.rs:2-33` documents all six touchpoints in order, in the module doc itself. This is the single best extensibility feature in the tree — a new contributor cannot miss it.

| # | Touchpoint | Where | Forced by |
|---|---|---|---|
| ① | Catalog row `Variant => "wire_name" @ Suite / Tier` + `pub mod <file>;` | `orchestrator/stage/mod.rs` (`define_stage_catalog!` macro at `:136-169`, rows `:175-344`; `RefreshSignedBundles` row at `:291`) | **Compiler** — a row without a tier token does not compile |
| ② | `OrchestrationStage` impl | new `stage/<name>.rs` (`refresh_signed_bundles.rs`, 95 prod lines) | Compiler (trait) |
| ③ | `Box::new(<Stage>)` arm in `build()`'s exhaustive match | `orchestrator/plan.rs:391-604` | **Compiler** — match is exhaustive over `StageId` |
| ④ | Absolute count assert `cli_ids.len() == N` | `vm_lab/mod.rs:38965` (assert at `:38989`, value 66) | Test (loud) |
| ⑤ | `StageSpec` registry entry | `crates/rustynet-cli/src/live_lab_stage_registry.rs` (`StageSpec` at `:392-434`; for-each-`StageId::ALL` registered assert at `:2974-2977`) | Test (loud) |
| ⑥ | MCP doc table + `EXPECTED` list | `crates/rustynet-mcp/src/bin/repo_context.rs:2080` (table) and `:2277-2286` (`orchestrator_stages_doc_matches_the_rust_planbuilder` string-equality gate) | Test (loud, cross-crate) |

Pipeline order is single-sourced: `StageId::ALL`, generated by the catalog macro, **is** the plan order (RNQ-16; `stage/mod.rs:136-169`). Stage ③ no longer carries order — the plan builder derives the planned list from `StageId::ALL` filtered by suite inclusion (`plan.rs:383-387`) and the match arm only instantiates. That is a genuinely good design decision: two of the three things a contributor could get wrong (order, placement) were deleted rather than documented.

### What is NOT forced, and what breaks if forgotten

The hand-maintained count pins. Measured in `plan.rs` tests:

- `build_returns_66_stages` `:615-618` (66)
- `chaos_suite_opt_in_appends_9_fault_stages` `:741-759` (75)
- `negative_control_opt_in_appends_4_control_stages` `:762-797` (70)

- canonical-order pin `build_returns_canonical_security_stage_order` `plan.rs:1006`

That is **up to 9 numeric literals + 1 order list** across 2 files. Which of them a given stage bumps depends on suite membership (a default-plan stage bumps the two 66-pins; an opt-in stage bumps only the opt-in pins — `refresh_signed_bundles` bumped 68/77/81). **Failure mode if forgotten: test failure, always loud, never silent** — this is tedium, not danger. One test already shows the better pattern: `skip_live_suite_drops_the_post_baseline_suite…` (`plan.rs:943-980`) uses *derived* lengths, not literals.

**Cost to add one stage, measured:** 1 new file + 5 edited files = **6 files touched**, of which hand-maintained (no compiler forcing): the ~2–9 count literals, the registry entry, and both MCP doc artifacts. Everything else fails compilation or a named test if missed. This is a good ratio.

## 3) The stage contract

`OrchestrationStage` (`orchestrator/stage/mod.rs:374-416`) declares: `id()`, `name()`, `dependencies()` (truth prerequisites — skip-cascade on fail/skip), `ordering_after()` (ordering-only, **no** cascade; an edge to a stage not in the plan is ignored), `applies_to_roles()` (empty = all), `fanout()` (`StageFanout::Once | PerNode`, `:366-371`), `execute()`, and `always_run()` (default false; exempt from dependency skip-cascade but still honors explicit `--skip-stage`).

`StageOutcome` (`orchestrator/error.rs:262-301`) has six variants: `Passed`, `Failed(String)`, `Skipped(String)` (reason mandatory by design — 33 prior empty-skip offenders motivated this, doc at `:266-281`), `NotRun`, `Reused{evidence_sha256}`, and `NotProven{reason, detail}`. `ReasonCode` (`:222-244`) types seven reasons (`missing_witness`, `unattributable`, `stale_evidence`, `unreadable_evidence`, `contradictory_evidence`, `fault_unverified`, `required_capability_absent`). `is_blocking()` (`:304-309`) = `Failed | NotRun | NotProven`; `Skipped` is non-blocking; `NotProven` is documented as blocking "we do not know" and must never be converted to skip/pass (`:290-300`).

**Can a stage do nothing and return `Passed`?** Not silently, anymore. The schema forces a reason on every non-pass outcome, and both historical offenders are now blocked by construction:

- **QH-70** (`QualityHardeningTodo_2026-07-25.md:6473+`, fixed in tree 2026-09-07, live proof pending): `mesh_status_validation` PASSED run 130201 with all four tunnel legs dead — it judged *configured* peers, not live tunnels, and also passed on an *empty* data block. The fix makes the evaluator judge daemon live-handshake fields (`path_live_peer_count`, `path_latest_live_handshake_unix`), fail partial meshes, check freshness on the guest clock, and reject vacuous empty-expectation passes. (Follow-up: `MeshStatusEvidenceReview_2026-09-08.md` found the first cut of empty-expectation rejection unsatisfiable; it was removed and the daemon-side gap filed as QH-81.)
- **QH-80** (`:6678+`, root-caused 2026-09-08, disposition OPEN): the stage logic was *correct* — the environment could never satisfy it. Two upstream defects (stale relay env override, `232fbec3`; `dns_zone` vs `dns-zone` extension drift, `70447b35`) kept `refresh_signed_bundles` skipping, so `relay_forwards_frame_validation` never once executed until run `live-lab-linux-relay-fwd11-20260908-005016` — which then failed after 90 s because the lab never mints a Relay traversal candidate (all four mint sites pass `relay_id: None` — `ops_e2e.rs:3773`, `:3792`, `:3946`, `:3939-3958`) and distributes no relay session material (no `relay_fleet` / `RUSTYNET_RELAY_SESSION` / `relay_session_token` anywhere under `vm_lab/`), so `load_relay_client` (`rustynetd/src/daemon.rs:4983`) returns `None`.

Skip-cascade semantics live in `runner.rs` `skip_decision` (`:211`): `always_run` exemption **first** (`:218` — ordering fixed after a real fail-open where explicit-skip was evaluated ahead), then explicit skips, then the dependency cascade (`:242-260`, blocking-dep name preserved in the `Skipped` payload, cascade continues transitively), then shutdown flag. The cascade triggers on `dep.is_blocking() || Skipped(..)` (`:235`) — a skipped dependency skips dependents. Cycle/unknown-dep detection happens at plan construction (`validate_plan` `:281`, `topological_order` `:306`), before any guest is touched.

**Silent-wrong risks in the contract:** `ordering_after` to a non-planned stage is silently ignored (documented, but a contributor can believe they created a constraint); `applies_to_roles()` returning the wrong set fails only at runtime; a stage that returns `Skipped` for a condition that should be `NotProven` converts a hole into a non-event — mitigated by the mandatory reason string, which at least lands in the ledger.

## 4) Offline testability — real infra exists, use it unevenly

The lab can be tested without guests, and the primitives are good:

- `RemoteShell` trait (`orchestrator/remote_shell.rs:143-199`: `read_file / write_file / stat / run_argv / tcp_send_recv`) with real SSH/SFTP/PowerShell impls and **`MockRemoteShell`** (`:1255+`: scripted responses, `set_stat_override`, `run_log`, `tcp_log`), tests in a separate `remote_shell_tests.rs`.
- A full **stub `NodeAdapter`** (~20 methods) in `stage/traffic_test_matrix.rs:390-484`.
- Stub stages exercising runner semantics (skip-cascade, `always_run`, timeouts) in `orchestrator/diagnostics.rs:1041-1358`; wrapper wrapping at `:539-567`.
- Runner behaviour tests using those stubs: `runner.rs:384-732+` — e.g. `ordering_after_does_not_skip_cascade` `:501`, `always_run_stage_runs_even_when_dependency_failed` `:611`, `always_run_cleanup_runs_even_when_explicitly_skipped` `:637`.

**Good examples:** the runner tests above prove *behaviour* against stubs. `refresh_signed_bundles.rs:155-234` tests metadata-vs-catalog, skip-when-not-elected, and fail-closed-without-assignments.

**Bad/borderline examples:** (a) `bundle_naming_pins` (`refresh_signed_bundles.rs:123-152`) asserts **source text** via `include_str!` — that no stage spells bundle names inline. It is defensible only because it pins a real live failure (the `dns_zone`/`dns-zone` drift of QH-80), but it is a shape assertion, not a behaviour test. (b) QH-70's original evaluator was exactly the failure mode offline tests did not catch: the stage's own logic looked correct against data that could never be meaningful. (c) `empty_ctx()` (`refresh_signed_bundles.rs:160-187`) **hand-constructs every `OrchestrationContext` field** — every new context field must be added here or the test fails to compile (loud, but it is a hand-maintained duplicate with no shared helper).

So: the harness exists and is genuinely good; the discipline of *proving behaviour rather than shape* is the uneven part, and QH-70/QH-80 are both cases where shape-passed and behaviour-failed diverged until a live run exposed it.

## 5) Adding an OS — the bolted-on axis

`NodeAdapter` (`orchestrator/adapter/node_adapter.rs:121`, `pub trait NodeAdapter: Send + Sync + Debug`) carries **53 `fn` declarations** (including defaults; e.g. `collect_os_version` `:127-128`). Per-OS implementations follow a principled family split — `adapter/{linux,linux_install,linux_traffic,linux_membership}.rs`, the same for `macos*` (plus `macos_exit_traffic.rs`), `windows*`, and stub `android.rs`/`ios.rs`. The split is real structure, not an accident.

But the adapter boundary does not hold. Measured: **`VmGuestPlatform::` appears 769 times outside `adapter/`** in the `vm_lab` tree. Production-code hotspots (test mods excluded): `vm_lab/mod.rs` 37, `role_validation/relay.rs` 14, `orchestrator/role.rs` 14, `stage/live_managed_dns_validation.rs` 10, `role_validation/anchor.rs` 10, `topology.rs` 9, `orchestrator/native.rs` 8, `overnight/backlog.rs` 7, `stage/security_audit_validation.rs` 7, `stage/host_cross_build.rs` 7, `network_audit.rs` 7, `stage/live_mixed_topology_validation.rs` 6, `role_validation/blind_exit.rs` 6, and ~11 more files at 3–5.

Two very different classes hide in that number:

1. **Legitimate capability gates** — `role.rs`'s `is_supported_for_platform` style checks ("may this role exist on this OS?"). These are correct at stage level.
2. **Inline behaviour branches** — a `matches!(platform, …)` inside a stage's execute path choosing a command, path, or assertion. Each is a **silent wrong-OS behaviour site for a new OS**: it compiles, the default arm runs, and the stage fails (or worse, passes vacuously) hours into a live run.

This assessment did not hand-triage all 769 into the two classes (see §9 limits), but the stage-level ones found incidentally (`live_managed_dns_validation.rs` 10, `security_audit_validation.rs` 7, `host_cross_build.rs` 7, `live_mixed_topology_validation.rs` 6, `exit_nat_lifecycle_validation.rs` 5, `live_extended_soak_validation.rs` 5) are mostly class 2. Real prior evidence this bites: `live_managed_dns_validation` hard-rejects any Windows-containing topology (`live_managed_dns_validation.rs:288-304`, documented in `LiveManagedDnsWindowsSupportScopingInvestigation_2026-09-05.md`), and the Windows post-enforce trace (`WindowsPostEnforceRuntimeLiveStagesAnalysis_2026-09-05.md`) found the `windows-dns-failclosed-check`/`windows-authenticode-check` structural mismatches exactly where Windows stages branched differently than Linux.

Also: `android.rs`/`ios.rs` stub files exist, advertising support that is not real.

**Cost to add an OS, measured:** implement the 53-method trait in a new adapter family (~3–4 files following the existing split), then **audit 769 reference sites** — with no compiler help distinguishing class 1 from class 2. That audit is the bolted-on part.

## 6) Adding a role validator

`orchestrator/role_validation/` holds 20 files (mod + 19 validators: `anchor`, `relay`, `admin_issue`, `blind_exit`, `blind_exit_dataplane`, `exit_nat_lifecycle`, `exit_demotion_residue`, `exit_dns_failclosed`, `dns_failclosed`, `key_custody`, `mesh_status`, `gossip_convergence`, `runtime_acls`, `ipv6_leak`, `service_hardening`, `security_audit`, `authenticode`, `signed_state_rollback_eval`, `secrets_not_in_logs_eval`, `identity_challenge`). Adding one is **one new file + one registration in `mod.rs` + a stage to invoke it** — fully additive, mirrors the stage recipe, and inherits the same `StageOutcome` fail-closed contract. This is the second-genuinely-modular axis. The residual risk is the same as stages: a validator that passes on shape (QH-70) or whose preconditions the environment never supplies (QH-80).

## 7) Good seams (named fairly)

- **`StageId::ALL` as the single order source** (RNQ-16) — deleted the order-maintenance problem outright.
- **The plan.rs module-doc recipe** (`plan.rs:2-33`) — self-documenting at the point of use.
- **`define_stage_catalog!`** — tier-token-required rows make the most common omission a compile error.
- **`distribute_bundle_kind`** — `refresh_signed_bundles` reuses it plus shared name constants from `distribute_assignments.rs` instead of re-minting (the shared-constant pattern is exactly what the `dns_zone`/`dns-zone` drift violated).
- **`RemoteCommand` + `ValidatedArg`** (`adapter/validated_args.rs`) — argv-only, validated remote exec; the right seam for platform-specific commands.
- **The `StageSpec` registry** (`live_lab_stage_registry.rs:392-434`) — one stage fully described as data (aliases, stream, budget, `proves: &[SecurityMinimumBar control IDs]` — coverage-as-code), with self-checking oracles spanning `StageId::ALL` (`:2974-2977`, `:2992-3003`, `:3059`–`:3202`).
- **`StageOutcome::NotProven` + typed `ReasonCode`** — the schema-level answer to "passed while proving nothing".
- **Mandatory `Skipped` reason strings** — after 33 empty skips, the type now demands the reason.

## 8) Weak areas, ranked by pain

| Rank | Weakness | Concrete failure | Discovered at |
|---|---|---|---|
| 1 | **Environment-completeness unguarded** — nothing validates that the lab supplies a stage's preconditions | QH-80: `relay_forwards_frame_validation` unreachable its whole life (no relay candidate ever minted, `ops_e2e.rs:3773/3792/3946/3939-3958`; no session material distributed) | **Runtime-worst: 90 s into its first-ever live run, 2026-09-08, months after being added** |
| 2 | **Platform scatter (769 refs outside `adapter/`)** — class-2 inline branches | Windows `windows-dns-failclosed-check` vs `windows_install.rs` pin mismatch; managed-DNS stage rejects Windows topologies outright (`live_managed_dns_validation.rs:288-304`) | **Runtime: 3 h into live runs**, or as never-executed dead branches |
| 3 | **Hand-maintained count pins (≤9 literals + order list + `mod.rs:38989` + MCP `EXPECTED` list)** | Forget one → named test fails; tedious on every stage add | **Compile/test time — loud, cheap, but recurring** |
| 4 | **MCP doc duplication** — `ORCHESTRATOR_STAGES` table (`repo_context.rs:2080`) + `EXPECTED` list (`:2286+`) are two hand-maintained copies of the catalog | Miss the `EXPECTED` entry → cross-crate test fails | Test time, loud |
| 5 | **`empty_ctx()` duplicates `OrchestrationContext` construction** (`refresh_signed_bundles.rs:160-187`) | New context field → every such helper must be updated | Compile time, loud |
| 6 | **`android.rs`/`ios.rs` stub adapters** | Advertise support that does not exist; a future reader may assume parity | Worse the later it is found |
| 7 | **Shape-vs-behaviour test discipline** (source-text pins, shape-passing validators) | QH-70 false-green | Was runtime; schema now blocks it by design |

Note the pattern in ranks 1–2: **the failures that hurt are runtime failures, and both classes are invisible to every compile/test gate that makes the stage axis so pleasant.**

## 9) Recommendations (work-item sized; prefer runtime→compile-time moves and deleting hand-maintained duplicates)

**Small**

1. **Derive the count pins.** Convert the seven `plan.rs` count tests and `vm_lab/mod.rs:38989` to derived lengths (pattern already exists: `plan.rs:943-980`), keeping exactly **one** absolute tripwire (the 66-pin) as the "did the default plan change shape" alarm. Deletes 8 of 9 literals; every future stage add stops bumping pins.
2. **Generate the MCP doc from `StageId`.** `orchestrator_stages_doc_matches_the_rust_planbuilder` (`repo_context.rs:2277-2286`) should build the `EXPECTED` list *from* `StageId::ALL` (+ per-stage registry metadata) instead of a second hand-typed list, so the doc table is rendered data and the test only checks formatting invariants. Deletes duplication, keeps the anti-rot forcing function.
3. **Shared test-context helper.** Extract `empty_ctx()` into one `orchestrator` test-support module used by all stage tests, so a new `OrchestrationContext` field is updated in one place.
4. **Label the stub adapters.** `android.rs`/`ios.rs` should carry a compile-time-visible `unimplemented!`-class marker or a doc note that they are placeholders, or be deleted until real.

**Medium**

5. **Platform-decision audit + capability table.** Sweep the 769 `VmGuestPlatform::` sites; classify capability-gate vs behaviour-branch; move class-2 behaviour into `NodeAdapter` methods (or a `PlatformCapabilities` table the stage queries). End state: a stage's execute path contains no platform `matches!`, and a new OS fails *compilation* on any unhandled capability. This is the single highest-value OS-axis fix.
6. **Declared environment preconditions.** Give stages a typed `requires()` (e.g. "relay candidate minted", "session material distributed") that the plan builder validates against what setup actually provisions, at construction time. QH-80 would then have failed offline on day one instead of month three at runtime. Design conservatively: absent declaration = stage must not assume (fail-closed default).

**Large**

7. **Data-driven plan inclusion.** `StageSpec` already describes suites, tiers, budgets, enablement, and platform rules as data (`live_lab_stage_registry.rs:392-434`). Let the plan builder read inclusion from the registry instead of the parallel suite→bool map and retention exceptions in `plan.rs:345-375` — collapsing catalog/plan/registry triple bookkeeping into one source. Big refactor; do after 1–2 have removed the noisy duplication.
8. **Per-OS stage-parity ledger as a gate.** Extend the registry's `platform_rule` so every stage declares per-OS support status (supported / fail-closed-skip / not-applicable), enforced by oracle tests, so "we added Windows to stage X" is a one-row change rather than a code hunt.

## 10) Honest limits

- Static reading at one commit (`0e649c65`) plus recorded run history; **no live run was launched for this assessment**.
- The 769 platform references were counted mechanically; the capability-gate vs behaviour-branch split (§5) is supported by the hotspot files inspected, **not** by a full hand-triage of all 769. Recommendation 5's audit is exactly that triage.
- QH-70's fix is live-proof pending; QH-80 is root-caused with disposition OPEN — both statuses are as of 2026-09-08 and may move.
- The 53-method `NodeAdapter` count includes default methods; the *required*-impl surface is smaller (the ~20-method stub in `traffic_test_matrix.rs:390-484` is representative).
- Line numbers drift; they were verified at this commit and are anchors, not API.
- This doc assesses *extensibility*, not lab correctness or security posture (see `QualityHardeningTodo_2026-07-25.md` and `SecurityMinimumBar.md` for those).
