# Live Lab Cross-Platform Custody / Secrets / ACL Stage — Adversarial Review (2026-09-01)

- **Reviews:** `documents/operations/active/LiveLabCrossPlatformCustodySecretsAclStageDesign_2026-09-01.md` (the GAP-6 design).
- **Method:** independent verification of every load-bearing design claim against the working tree at the review commit: the orchestrator stage/adapter/role-validation sources under `crates/rustynet-cli/src/vm_lab/orchestrator/` (note: the design's citations omit the `orchestrator/` path segment), the daemon posture modules under `crates/rustynetd/src/`, and the standalone live-lab binaries under `crates/rustynet-cli/src/bin/`. Every quoted line range below was read in this tree, not taken from the design.
- **Verdict:** **READY-WITH-AMENDMENTS.** The grounding verdict (PARTIAL), the gap statement, and the wiring plan all check out, and the design proposes purely additive surface with no weakening of existing validators. One substantive wording defect must be fixed before implementation (amendment A1 — the design's macOS/Windows custody expectations reference a "custody watcher" that does not exist anywhere in the codebase), plus one pattern-completeness amendment (A3) and several smaller tightenings.

---

## 1. Attack 1 — re-verifying the grounding verdict (CONFIRMED)

The design's §1 verdict of **PARTIAL** is accurate in both directions; it neither over-claims nor under-claims.

**Posture validators for key custody and runtime ACLs exist and execute on macOS and Windows today.** Verified end to end:

- `role_validation/key_custody.rs` gates `key_custody_runtime_implemented` (lines 15–20) return `true` for Linux, macOS, and Windows; `validate_macos` (42–55) and `validate_windows` (57–70) invoke `run_argv` with the daemon subcommand (`macos-key-custody-check` / `windows-key-custody-check`) and evaluate the report. `role_validation/runtime_acls.rs` mirrors this exactly (`{platform}-runtime-acls-check`).
- `rustynetd/src/main.rs` registers all six subcommands in one dispatch: `windows-runtime-acls-check` (355), `windows-key-custody-check` (367), `linux-runtime-acls-check` (394), `linux-key-custody-check` (400), `macos-runtime-acls-check` (427), `macos-key-custody-check` (433); each accepts `--no-fail-on-drift`, and drift failure strings exist (e.g. `windows-key-custody-check reported drift…` at 1141, `macos-key-custody-check reported drift…` at 1805).
- `supports_role_validator` has exactly **one** definition in the repository — the trait default at `adapter/node_adapter.rs:259–272` — which returns `true` for Linux/MacOS/Windows for every kind except `GossipConvergence` (which consults its own gate). No adapter overrides it. So the KeyCustody/RuntimeAcls posture gates are effectively inert today: the validators run unconditionally on all desktop platforms.

**Adversarial live custody and secrets-in-logs are Linux-only.** Verified: `stage/live_key_custody_validation.rs:48–67` dispatches unconditionally to `--bin live_linux_key_custody_test` with no platform branch; `stage/live_secrets_not_in_logs_validation.rs` (167 lines) dispatches unconditionally to `--bin live_linux_secrets_not_in_logs_test` the same way. `RoleValidatorKind` (`node_adapter.rs:75–86`) contains no `SecretsNotInLogs`, and the `role_validation/` directory contains no secrets module — the design's claim that secrets-in-logs has **no validator at all** off Linux (not even a posture layer) is confirmed.

**Windows live-stage gating (§4.7 prerequisite).** Confirmed authoritative: `node_adapter.rs:519–524` carries the verbatim comment that the Windows control CLI has no `status` subcommand ("a KNOWN deferred §4.7 gap"), and the identity challenge (463–479, executed at 525–530 *before* validator dispatch) fails closed on `NotLiveAssertion` with a `§4.7 node-identity challenge rejected` protocol error. Windows live validators will skip until that subcommand lands; the design's §4.3 reported-skip handling for this case is the correct treatment.

## 2. Attack 2 — the doc-drift claim (CONFIRMED)

`key_custody_validation.rs:19–21` states verbatim that a macOS/Windows node is "reported-skipped … on the [`key_custody_runtime_implemented`] posture gate," and `runtime_acls_validation.rs:17–20` says the same for ACLs. Both are stale: the gates return `true` on all desktop platforms *and* `supports_role_validator` never consults those gates for these validator kinds, so the reported-skip branch is dead code today — macOS and Windows nodes execute these validators and the skip path is never taken. The skip machinery itself is sound when it does fire (the reported-skips JSON names every skipped alias+platform, and `outcome_for` turns skips-only into `StageOutcome::Skipped`, never `Passed`, with tests pinning all three outcomes at 113–150) — so this is purely a stale-comment defect, exactly as the design classifies it. The design already schedules the comment correction as prerequisite §8(4); this review pins the exact lines to fix: `key_custody_validation.rs:19–21` and `runtime_acls_validation.rs:17–20`.

## 3. Attack 4 — the new `SecretsNotInLogs` validator fits without weakening (SAFE, with A3)

The proposed addition — a `RoleValidatorKind::SecretsNotInLogs` variant, dispatch legs, a new `rustynetd secrets-not-in-logs-check` subcommand, per-platform `validate_*` functions beside the existing six evaluators, and a PerNode stage with the same reported-skips contract — follows the established pattern precisely (the six existing subcommands, the single `supports_role_validator` default, and the KeyCustody stage as template were all verified above). It is purely additive: no existing validator, evaluator, or the identity challenge is modified. The default of desktop-supported day one (following the KeyCustody precedent rather than adding a new gate) is consistent with how the sibling validators actually behave today.

The one weakness is §5.1's description of what the daemon self-check scans for: "the repo's forbidden secret patterns (private-key block markers, enrollment-token shapes, share/preshared-key fields)." No canonical list of such patterns exists in the repo to cite — the secrets-hygiene gate script is a thin wrapper over a Rust binary with no greppable pattern table, and the security-audit module defines none either. The only *proven* pattern set in the codebase is the live binary's three scanners: 64-char hex (a WireGuard 256-bit private key), 32-char hex (an ed25519 key), and base64 EC-key header prefixes (`live_linux_secrets_not_in_logs_test.rs`, scanning journald; its doc comment targets "never log ed25519 signing keys, enrollment secrets to journald"). Amendment **A3** pins this.

## 4. Attack 5 — adversarial custody assertions on macOS/Windows (RISK — the substantive finding)

**No custody watcher exists on any platform.** This is the design's one substantive defect.

- `rustynetd/src/macos_key_custody.rs` is a pure check-time posture module: `collect_macos_key_custody_report()` builds entries via `probe_required_dir` / `probe_required_file` / `probe_forbidden_file`, and `evaluate_macos_key_custody` is a pure evaluator whose `overall_ok` is `drift_reasons.is_empty()`. Custody contract: keys dir `rustynetd:rustynetd` mode `0600`, key files `0640`/`0600`. There is no continuous watcher, no drift flag, no auto-remediation, and no startup-enforcement logic in the module.
- `rustynetd/src/windows_key_custody.rs` has the same shape: `collect_windows_key_custody_snapshot()` + `evaluate_windows_key_custody(entries) -> Result<(), Vec<String>>`, no watcher, no remediation.

Meanwhile the actual Linux adversarial semantics that the design claims to "match" are **restart-based**, not watcher-based. `live_linux_key_custody_test.rs`: baseline `initial_mode_ok` → chmod the key to `0644` via sudo (line 125) → **restart the daemon** → `rejection_confirmed = daemon_rejected || custody_log_found` (the daemon fails to become active, or the journal carries a custody error; 140/142–154) → restore `0600` (162) → **restart again** → `daemon_recovered && final_mode_ok`; the overall pass is the conjunction `initial_mode_ok && rejection_confirmed && daemon_recovered && final_mode_ok` (184), with per-stage booleans in the report JSON and a matrix row appended.

Design §3 expects macOS "rejection via daemon custody watcher drift flag OR drifted status from follow-up check — matching rejection semantics the Linux binary asserts." Both halves are problematic: (a) the watcher half references a mechanism that does not exist anywhere; (b) the follow-up-check-only half is **strictly weaker** than Linux. A macOS test that chmods the key, runs `macos-key-custody-check`, observes drift, restores, and passes has proven only that the *checker* sees the drift — the daemon may have been running happily with a world-readable key the whole time. That is a false pass relative to the Linux bar and must not be accepted as "matching rejection semantics."

**Amendment A1 (required).** Reword §3 and §4 to delete all "custody watcher" phrasing and pin the acceptance to the Linux binary's actual stage sequence, adapted per platform:

- macOS: baseline custody check `overall_ok` → chmod attack → **restart via launchd** → rejection asserted as "daemon failed to start/stay active OR `macos-key-custody-check` reports drift (or a custody log line in the launchd sink)" → restore → restart → recovery + final check clean.
- Windows Attack A: ACL grant via the `rustynet-windows-native` argv-only helper (never `icacls` shell strings) → **service restart** → rejection via "service failed OR `windows-key-custody-check` reports drift" → revert ACL → restart → recovery.
- State explicitly that detection is check-time plus restart unless a continuous watcher is later added, and that a daemon still running with a downgraded key at assertion time is a **failure**, not a pass.

Amendment **A2** (keep + tighten): the passive DPAPI probe (§4 Attack B) stays as designed — copy the blob to a temp location and assert it is inert via the custody check's status plus hashes/sizes only; the test must never attempt decryption, and it should not read or transmit key material.

## 5. Attack 6 — secrets hygiene of the new tests (SAFE, with precedent to preserve)

The Linux binary already demonstrates the correct discipline: the enrollment trigger uses `rustynet enrollment mint --secret <path> --ttl <secs>` and logs only `token len={}` (line 149) — length, never content; the scanners match *shapes*, and no secret is read into the test process. The design preserves this: no Keychain extraction (§3.4 non-goal), passive DPAPI probe, and the secrets live test inspects only the daemon's own sink (§5.3 non-goal). The one hygiene consideration is to carry the same discipline into the new macOS/Windows binaries — log lengths and booleans, never content — which the design's "no secret material read/logged/transmitted" clauses already require. Keep as written; A2's hash/size-only constraint covers the DPAPI side.

## 6. Attack 7 — fail-loudness (SAFE)

The stage layer's outcome resolution is verified: `outcome_for(failures, skips)` — any failure → `Failed`, skips-only → `Skipped` (with a message stating no node executed), otherwise `Passed` — with tests pinning all three outcomes and the reported-skips note naming every skipped node (`key_custody_validation.rs:113–150`; `runtime_acls_validation.rs` mirrors). Live-stage failures route through `format_stage_binary_failure_with_log` (QH-09 discipline) with the log path attached. A Windows live custody stage parked behind §4.3's reported-skip therefore resolves to `Skipped`, never `Passed`. One residual: amendment **A4** — on a node without the enrollment secret, the live secrets test cannot exercise the enrollment path at all (the Linux binary deliberately seeds the secret on admin nodes only, so absence is a detectable non-exercise). The macOS/Windows mirrors must surface "secret absent → stimulus path not exercised" as a reported limitation in the report artifact rather than folding the check into a pass. The design's §2 principles imply this; make it explicit.

## 7. Attack 8 — weakening of existing surface (NONE)

The design touches exactly one existing stage file surface: the per-platform dispatch extension in the two live stages (§6), which reuses `ssh_params_for_role` (verified: user defaults Linux→`root`, macOS→`admin`, Windows→`administrator` at `live_key_custody_validation.rs:111–137`, so the design's "Windows daemon driven via SSH as administrator" is grounded), the failure formatter, and the outcome resolution verbatim. Dependency wiring checks out: `LiveKeyCustodyValidation` already declares `deps = [LiveSecretsNotInLogsValidation]` today (stage line 23), and `LiveSecretsNotInLogsValidation` depends on `LiveRebootRecoveryValidation` — matching design §6's table. No existing validator, evaluator, gate, or the identity challenge is weakened anywhere in the plan.

## 8. Amendments

1. **A1 (required, §3/§4):** Remove "custody watcher drift flag" phrasing — no watcher exists on any platform (`macos_key_custody.rs` / `windows_key_custody.rs` are pure check-time collect+evaluate). Pin restart-based rejection semantics mirroring `live_linux_key_custody_test` (baseline → chmod/ACL attack → restart → rejection = daemon-failed OR custody-check drift → restore → restart → recovery), and require that a daemon still running under a downgraded key at assertion time fails the test. Detection on macOS is launchd restart + `macos-key-custody-check`; on Windows, native ACL helper + service restart + `windows-key-custody-check`.
2. **A2 (§4 Attack B):** DPAPI probe asserts inertness via custody-check status plus hash/size only; never attempt decryption; log no key material.
3. **A3 (required, §5.1):** Pin the new `secrets-not-in-logs-check` pattern list concretely. The repo has no canonical forbidden-pattern table; the proven precedent is the live binary's three scanners (64-hex WireGuard key, 32-hex ed25519 key, base64 EC-key headers). Define the checked shapes explicitly in the design so `overall_ok=true` is meaningful evidence, and note any additional shapes as new scanner requirements rather than unstated assumptions.
4. **A4 (§5.2):** The macOS/Windows live secrets binaries must treat "enrollment secret absent on the node → stimulus path not exercised" as a reported limitation in the report artifact, never as a pass; mirror the Linux binary's real-stimulus requirement (its own comment at lines 113–118 records that a former generate-only stimulus was removed as a false-pass mode — a weak stimulus is a *known* failure mode here, not a hypothetical).
5. **A5 (§8 prereq 4):** Keep the doc-comment correction prerequisite; exact stale lines are `key_custody_validation.rs:19–21` and `runtime_acls_validation.rs:17–20`.
6. **A6 (citations):** Two minor fixes in §1: the dispatch-table citation "532–568" should read "532 onward" (the `MeshStatus` and `DnsFailclosed` legs continue past 568; the KeyCustody/RuntimeAcls legs the design relies on are fully inside the cited range, so this is cosmetic), and the path citations should include the `orchestrator/` segment (`crates/rustynet-cli/src/vm_lab/orchestrator/{role_validation,stage,adapter}/…`).
7. **A7 (keep):** Windows live custody/secrets stages remain reported-skipped behind the §4.7 `status` subcommand gap until it lands — design §4.3 already specifies this correctly; retained as an amendment only to record the review's confirmation of the gating mechanism (identity challenge fails closed at `node_adapter.rs:463–479, 525–530`).

## 9. Under-claim check and confidence

The design is, if anything, slightly conservative: §1.1's "posture validators exist and execute" is fully proven (including the single-definition `supports_role_validator` and the six daemon subcommand registrations), and §1.2's "Linux-only" gap claims are exact. Two honesty notes for the record: (a) the §1.3 ledger-attribution line references in `live_lab_run_matrix.rs` (lines 211/212/3767/3880/4842/4843/4884) were not independently re-opened in this review; the design's characterization of them as attribution strings rather than evidence is consistent with the ledger's structure and was accepted at low risk. (b) The design's own live-proving status is honestly `NONE` (§7: lab VMs were down on the design date); nothing in this review changes that — parity claims remain gated on §8 prerequisites and green rows in `documents/operations/live_lab_node_run_matrix.csv` with verdicts taken from stage report artifacts, exactly as §9 states.

**Overall: READY-WITH-AMENDMENTS.** With A1 and A3 applied before implementation (A2/A4–A7 alongside), the design is sound, purely additive, and correctly scoped to close the GAP-6 parity gap it names.
