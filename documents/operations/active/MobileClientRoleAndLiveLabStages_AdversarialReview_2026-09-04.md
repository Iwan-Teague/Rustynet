## 3. Wrong, imprecise, or missing

### 3.1 The mandate is self-declared (most important finding)

The reviewed doc's framing hangs on "Mandate: CrossPlatformRoleParityPlan §2 + Refresh §1". **Neither mandates mobile.** `CrossPlatformRoleParityPlan_2026-06-21.md` §2 is titled "What 'parity' means per role (must hold on macOS AND Windows)" and enumerates client/admin/anchor/exit/blind_exit/relay/nas/llm — no iOS, no Android, no mobile. Worse, `CrossPlatformRoleParityRefresh_2026-07-23.md:64` explicitly disclaims it: "*like mobile clients, not a parity gap (corrected 2026-06-24)*". The mobile program is therefore a **new scope proposal**, and the doc should say so and route it through the ledger-owning docs rather than citing a mandate that does not exist. As written it launders a proposal into a release-blocking obligation.

### 3.2 §1.4 widens 2 of ≥5 fail-closed mobile gates — the plan dead-ends

The doc's promotion order widens only `is_lab_assignable_for_platform` then `is_supported_for_platform`. The tree rejects mobile in at least five places, four of which the doc never names:

1. `is_lab_assignable_for_platform` — `orchestrator/role.rs:110` (doc has this one).
2. `is_supported_for_platform` — `orchestrator/role.rs:93-94` (doc has this one).
3. **`daemon_node_role_for_platform`** — `orchestrator/role.rs:172-174`: `Ios | Android => Err("{platform:?} has no supported daemon role mapping")`. Without a new arm, no lab role can be translated into a daemon posture for a phone even after (1) and (2) widen.
4. **`product_capabilities_for_platform`** — `orchestrator/role.rs:183-185`: `Ios | Android => Err("{platform:?} has no supported product capability mapping")`. This is the gate that actually emits the signed capability set; the doc's §1.3 "phone gets only `RoleCapability::Client`" matches the existing `Client` arm's shape (`role.rs:239-242`) but is unreachable until this arm widens.
5. **`TryFrom<VmGuestPlatform> for TopologyPlatform`** — `vm_lab/topology.rs:109-111`: "mobile platforms cannot host topology roles" — every topology-resolution path the doc's §4.2 selector plan relies on fails here first.

Plus the two execution-layer rejections the doc correctly diagnoses but does not list as widening work: `bootstrap/mod.rs:125-130` and `remote_shell.rs:313-325`. The doc's §1.4 "same commit" table-update claim also silently assumes the matrix comment at `role.rs:61-71` is the only doc-in-code surface; it is not — the error strings themselves are the contract. Net: the §1.4 plan, executed exactly as written, produces a phone that passes the role gates and then fails at role translation, capability emission, topology resolution, bootstrap, and remote shell. **Fix: §1.4 must enumerate all seven sites (5 + 2) in one widening commit or sequence them explicitly.**

### 3.6 Enrollment transport: reuse claim holds for the token, glosses the consumer

§2.1's "reuses the signed single-use token flow unchanged" is accurate for **issuer-side** primitives (all verified above) — a QR/deep-link/`adb`/`simctl` delivery is an opaque-transport change and the HMAC-tag bearer model does not care. But the enrollee side is net-new surface the doc waves through: today the only consumers are the CLI/IPC verbs (`enrollment_consume.rs:6-7`) and the anchor endpoint is gated on `require_local_signed_capability` (`daemon.rs:1315`, `2009`). A phone enrolling needs an HTTP/endpoint client that speaks the anchor's enrollment protocol plus the same membership-ingest path Linux uses; none of that exists in-tree, and no QR/deep-link code exists anywhere in `crates/` today. §2.2 should state plainly that the transport *and the enrollee client* are new product surface, with the negative test (over-broad capability bundle rejection) hooked to the `product_capabilities_for_platform` widening from §3.2 above.

## 4. Bottom line

The doc's §3–§4 (stage catalog integration, selector wiring, ledger columns, fail-loud semantics) is high-quality and survives verification nearly line-for-line. Its §1 gate inventory is materially incomplete (§3.2 here) and its mandate framing is unsupported (§3.1 here). With §1.4 expanded to the full seven-site widening list, §0.4's count fixed, and the `lab_state.rs` cites corrected to `vm_lab/mod.rs:21222`, this is a sound execution plan for a **newly-scoped** mobile program — one that should be entered into the active ledgers as a proposal, not presented as the already-mandated parity work the cited documents never ordered.
