## 1. S1 — the 30 s posture re-assert and the one-reapply latch

### S1-A1. Can the latch enter a re-apply loop? Is one apply per cadence the true bound for a flapping service? — CONFIRMED-SAFE (rate-bounded), with one structural pin required (S1-A2)

**Loop construction attempt.** The loop would need drift → heal → immediate re-drift → heal inside one cadence. The design's latch (`dns_posture_reassert_pending`, design §2.2.2/§2.2.5-6) is a boolean cleared only by a successful apply, and the heal is the FULL generation apply (`apply_dataplane_generation`, `daemon.rs:10453-10480`), which runs its own `assert_dns_protection` immediately after `apply_dns_protection` (`phase10.rs:6766-6770`). A heal that does not stick therefore fails *inside the apply*, does not clear the latch, and enters the reconcile ladder — it cannot come back as "success, re-drift next tick." The shortest honest cycle is: drift at cadence tick N → apply at tick N+1 (1 s later) → success clears latch and restarts cadence → next assert ≥ 30 s later. So the worst-case repetition rate for a flapping service (one that toggles or re-writes its DNS faster than the daemon heals) is **one full apply per ~31 s, indefinitely** — bounded rate, unbounded duration. That is the same shape as QH-54's accepted 30 s re-assert, and design test 6 (`dns_posture_drift_clears_after_successful_apply_even_if_next_assert_fails_again`, design §2.4) pins exactly this. Additional protection the design inherits: `apply_dns_protection` sets `dns_protected = true` first and never reverts it on SC failure (`phase10.rs:4558`, comment `phase10.rs:4574-4578`), so a failing heal keeps the pf floor rendered throughout — the loop cannot open a :53 hole while it churns.

**Residual honest note (accepted, not a mitigation demand):** the "one apply per drift episode" phrasing in design §2.3 is rate-accurate only because the cadence restarts on the heal. If a service flaps on a ~30 s period, the node performs one full generation apply every ~30 s forever — pf re-render, full re-pin, audit/stage-marker traffic. This is deliberate churn-bounding, not a defect; the live drill in design §5.2 ("exactly one extra apply, no churn loop") is the right acceptance check.

### S1-A2. Is assert/apply mutual exclusion per pass actually guaranteed by the branch structure? — RISK (implementation pin; the design's wording is right but not yet forced)

The predicate `will_apply_generation` is evaluated **twice** per pass: first at `daemon.rs:10329-10333` (stored, `daemon.rs:10334`), then re-read in the branch condition at `daemon.rs:10348-10350` — deliberately, because the QH-04 traversal refreshes between the two reads (`daemon.rs:10335-10341`, rationale comment `daemon.rs:10343-10347`) can themselves flip `controller.state()` to `FailClosed` or `restriction_mode` to `Recoverable` mid-pass. A pass can therefore have `will_apply_generation == false` at the first read and the apply block still execute at `daemon.rs:10348`.

The design says the assert runs "at the tail of each reconcile pass, in the branch where the apply block did not run (i.e., `!will_apply_generation` after the re-read at `daemon.rs:10348-10350`)" (design §2.2.3) and that the branches are "mutually exclusive within a pass" (design §2.3, test 6). The only structure that makes that guarantee TRUE is: the assert is the **`else` arm of the exact `if` at `daemon.rs:10348-10351`**. If an implementer instead gates on `!will_apply_generation` (the first read) at the pass tail, a pass whose FailClosed/Recoverable flipped true between the reads runs **both** the apply and the assert — the exact "observation noise enters failure accounting" pollution design §2.2.3's health gate exists to prevent (the assert fires, fails against a restricted node's posture, and its error handling races the apply's).

**Required mitigation (design amendment):** §2.2.3 must name the structure, not just the timing: "the assert lives in the `else` arm of the `if` at `daemon.rs:10348-10351`, keyed on the same re-read condition; it is not a tail call beside `maybe_reassert_host_firewall_admission` (`daemon.rs:10601`), which deliberately runs after *every* pass." Add a unit test: traversal-refresh-fails-closed mid-pass ⇒ apply runs, assert does not.

Note there is **no `else` today** — the apply block ends at `daemon.rs:10599` and the tail (`daemon.rs:10601-10606`) runs unconditionally — so this is new structure, not a reuse of an existing exclusion. Pinning it is cheap; leaving it to implementation discretion is where the bug class lives.

### S1-A3. Does the heal ever destroy a legitimate DNS change, and does the capture preserve the user's value as rollback baseline? — CONFIRMED-SAFE (owner-decreed semantics), one under-claimed semantic recorded

The drift response is the full apply path, so the question reduces to the M1 capture semantics, which are already hardened: the capture loop (`phase10.rs:4607-4620`) reads each service's current DNS *before any mutation* and resolves it through `resolve_backup_baseline_entry`. The semantics (gap doc §7 hardening entry, enforced by the guard comment at `phase10.rs:4584-4593`): a normal non-loopback capture is **recorded unchanged** — so a user's manually-set resolver becomes the recorded rollback baseline, exactly as design §2.2.5 claims; loopback residue with a readable prior backup **preserves the prior entry** (the real pre-enforcement original — this is what makes repeated heal cycles non-degrading: heal N captures loopback, the backup keeps the user's value); loopback residue with no prior entry **refuses the apply loudly**; a present-but-unreadable prior backup refuses before any baseline is built (`phase10.rs:4596-4606`). The drift assert itself (`phase10.rs:4687-4731`) is pure observation — it enumerates and reads, mutates nothing.

**Fighting legitimate changes:** under the owner's scope decree (gap doc §5.2; design §1 decree 2), while `protected_dns` is active the daemon owns SC DNS for all enabled services; a manual edit during protection is drift by definition. The adversarial case — a VPN client writing its own resolvers and getting re-pinned within 31 s — is the *pre-existing owner sub-decision* (gap doc §7: "VPN/utun services … NOT special-cased"), not a new S1 behavior; S1 only makes the decree enforce itself continuously instead of never. The escape hatch (config exclusion list) remains the owner's reserved remedy. No silent carve-out is added. CONFIRMED.

**Under-claimed semantic (record, not amend):** latest-wins means once a user edit is captured, the *original* pre-protection value is gone from the backup — a later teardown restores the user's last edit, not the factory DNS. That is today's documented M1 semantics; S1 makes overwrite events more frequent (each heal re-affirms it). Worth one sentence in the design's §2.3 so an operator is not surprised that "restore" returns their own last edit.

### S1-A4. Does routing heal failure through the existing ladder avoid double-count and premature-permanent, and is detection kept OUT of the failure count? Does `RestrictionMode::Recoverable` forcing `will_apply_generation` create unbounded retry vs the 5-strike cap? — CONFIRMED-SAFE on counting; RISK recorded on what "permanent" actually means (pre-existing)

**No double-count.** Detection sets only the latch + `last_reconcile_error` (dedup pattern per `daemon.rs:10299-10302`); `reconcile_failures` is untouched at detection (design §2.2.5 is explicit). The heal is one apply; its failure bumps once via the existing arm (`daemon.rs:10571-10578`, mirrored `:10579-10597`). No path counts a drift episode twice.

**No premature-permanent from accumulated strikes.** `reconcile_failures` resets to 0 on every successful apply (`daemon.rs:10559`), and promotion needs `>= max_reconcile_failures` (`daemon.rs:10796-10803`, `DEFAULT_MAX_RECONCILE_FAILURES = 5`, `daemon.rs:522`). So five failures must be **consecutive**: one transient helper blip during a heal is one strike, wiped by the next success. A node cannot drift to Permanent across weeks of unrelated single failures.

**Detection-out-of-count is a deliberate deviation from the nearest precedent — say so.** QH-54's tail re-assert *does* count its own failure directly (`daemon.rs:10644-10651`: bump + `restrict_recoverable` + promote). S1's detection does not, because QH-54's failure is itself a broken enforcement state, while S1's assert failure is an observation that the *next tick's heal* will act on — and the heal's failure is what counts. This asymmetry is correct; a future reviewer comparing the two call sites side by side should not "normalize" S1 to count at detection. The design states the rule (§2.2.5 "Do not bump") but should name the QH-54 contrast explicitly so the divergence reads as decided, not accidental.

**RISK (recorded, pre-existing, made more reachable by S1): "Permanent" caps escalation, not attempts.** After promotion, `restrict_recoverable` deliberately keeps recording new failures (QH-55, `daemon.rs:10757-10766`), and a Permanent node's controller sits in `DataplaneState::FailClosed` (set by `force_fail_closed_or_restrict`, `daemon.rs:10779-10794`), which keeps `will_apply_generation` true (`daemon.rs:10329`) — so the full apply block **retries every 1 s tick indefinitely**, each attempt re-failing against a dead helper and re-recording. The 5-strike cap bounds how fast the node escalates; nothing bounds the retry rate afterward. This is the existing behavior for every failure class (nothing S1-specific), but S1 adds a new driver into that machinery: a permanently drifted service with a dead helper = a 1 Hz full-apply hammer (pf render + enumerate + N×getdns against a dead socket, each waiting out `privileged_helper_timeout_ms`). Fail-closed throughout — but "within 5 attempts (~5-6 s)" (design §2.3) describes escalation only, then the hammer starts. **Required mitigation (doc-level):** design §2.3's residual list must state that post-Permanent the heal retry continues at tick rate by design (fail-closed, operator-visible via QH-55 recording), so nobody later "fixes" the observed retry storm as a regression. A backoff would be a separate change (one-execution-path rule; not smuggled into S1).

**Stale-latch check (clean):** the latch is cleared on success next to `pending_generation_apply` (`daemon.rs:10483` region, design §2.2.6); `restriction_mode` returns to `RestrictionMode::None` only in the same success arm (`daemon.rs:10557`). There is no path where the node returns to healthy with the latch still set.

### S1-A5. Is 30 s defensible, and what does the privileged round trip cost / interact with? — CONFIRMED-SAFE, two bounds named

The cadence has two shipped precedents at the exact proposed site: QH-54's `HOST_FIREWALL_ADMISSION_ASSERT_INTERVAL_SECS = 30` (`daemon.rs:486-497`) for a privileged re-assert that must not ride the 1 s tick, and QH-39's `STATE_SNAPSHOT_HEARTBEAT_INTERVAL_SECS = 30` (`daemon.rs:499-521`) for precisely the "healthy converged node performs no periodic action because none of the five disjuncts holds" structural gap (comment verbatim at `daemon.rs:504-506`). The cadence-timestamp field precedent exists (`last_host_firewall_admission_assert_unix: Option<u64>`, `daemon.rs:4640`).

**Cost accounting (verified):** one assert = in-process ruleset render + substring checks (`phase10.rs:4693-4706` — `render_pf_rules`, no `pfctl` exec) + 1 service enumeration + N per-service `getdns` helper round trips (`phase10.rs:4712-4718`). Per 30 s that is the same order as QH-54's single D-Bus round trip, for any realistic N. Two bounds the design inherits and should name:

1. **The assert is synchronous on the reconcile thread.** A slow helper socket stretches one reconcile pass to at most `privileged_helper_timeout_ms` (the same knob the startup guard passes, `daemon.rs:11591`) — one delayed tick, not a hang. QH-54 lives with the identical property (`daemon.rs:10629-10653` is also synchronous on the tick). Acceptable; name it.
2. **The cadence timestamp must advance on attempt, not success.** Design §2.2.3 says "since the last successful (or attempted) posture assert" — the *attempted* half is load-bearing and matches QH-54's set-before-call pattern (`daemon.rs:10642`). If an implementation advances the timestamp only on success, a persistently-failing assert re-fires every 1 s tick: privileged hammering plus per-tick `last_reconcile_error` churn. Pin this in the design text (it is currently parenthetical) and in test 2 (§2.4).

**One under-claim to record (not a defect):** the pf half of `assert_dns_protection` validates the **rendered** ruleset, not the live pf anchor (`phase10.rs:4693-4706`). S1 therefore re-detects SC posture drift and renderer drift, but NOT an externally-flushed anchor (boot-time `pfctl -F` is fine — the next apply re-renders — but an operator/other-tool anchor flush on a healthy node is invisible to S1). Design §2.3's "the pf floor bounds the leak" argument presumes the anchor is live; the live-anchor check belongs to S6's stage and the next generation apply. One sentence in §2.3 keeps the claim honest.

### S1-A6. Is periodic-only adequate versus the rejected SCDynamicStore path, given non-:53 channels (DoH to allowed endpoints without a :53 exclusion)? — CONFIRMED-SAFE (adequate), with the exposure correctly characterized

Constructed worst case inside the ≤31 s window (cadence + tick, design §2.3): SC posture advertises real resolvers on a drifted service. What actually leaks at the packet layer: **nothing on :53** — the interface-agnostic labeled `rustynet-dns-block-lan-{udp,tcp}` blocks render whenever `dns_protected` is true (`phase10.rs:3451-3459` per the design's own §1; renderer verified in the adversarial review §3 across all knob combinations), and `dns_protected` stays true through the entire drift/heal cycle (`phase10.rs:4558`, `4574-4578`). The non-:53 channels (app-level DoH/:443 via the endpoint pass rules `phase10.rs:3496-3505` which carry no :53 exclusion; mDNS :5353; resolver cache) are **independent of SC posture** — pinning never closed them (adversarial review §2 lists them as standing side doors of M1 itself). So the drift's *marginal* exposure over the protected steady state is: the advertised posture (mDNSResponder holding real resolvers whose queries die at pf) and the S6 oracle divergence (lab RED while daemon green) — real operational costs, correctly priced in design §2.1/§2.3, and a change-triggered fast path would reduce the window from ~31 s toward ~0 **without changing either cost's nature**. The rejected alternative's costs (new async event source in the reconcile state machine, new platform API surface, missed-event failure modes, harder deterministic tests — design §2.2 closing paragraph) are structural and permanent; the periodic window is bounded and self-healing. The design's decision is sound, and the layering path (a future notification fast path behind the same latch) is preserved.

One sequencing note for the interim: until S1 lands (order S6 → S4 → S1, design §4.2), the drift window is the pre-S1 *unbounded* one — S4's landing does not shorten it. Anything reading the S4-only interim state as "drift bounded" would be wrong; the bound exists only once S1 lands.

## 2. S4 — the widened startup residue observation

### S4-A1. Can a service set changing mid-observation produce an inconsistent verdict, and does failing the whole observation on any per-service error avoid acting on a partial view? — RISK (the design implies all-or-nothing but never states it)

Design §3.2.1 defines a per-service classification (`None` / `LoopbackOnly` / `NonLoopback`) and a binary helper result (`Observed(classification)` or `ObservationUnavailable(reason)`), but nowhere states the error-mapping rule: **any** enumeration or per-service read error must fail the WHOLE observation into `ObservationUnavailable`. The ambiguity matters because the sibling paths are all-or-nothing and S4 must match them: the runtime assert returns on the first per-service read error (`phase10.rs:4715-4718`), and the enumeration parser aborts the whole apply on a single invalid line (adversarial review §5). A best-effort partial observation would classify a service that *errored* as not-loopback-by-absence and could return `Observed` over an incomplete view — missing exactly the residue S4 exists to find, while reporting a clean observation.

**Required mitigation (design amendment):** one sentence in §3.2.1 — "any enumeration or per-service `getdns` error ⇒ `ObservationUnavailable(reason)`; a partial observation is never returned" — plus a test alongside §3.4's list: `observation_unavailable_on_any_per_service_error` (fake helper fails one service's read mid-list ⇒ `ObservationUnavailable`, not a partial classification).

**TOCTOU under that rule (clean once pinned):** a service disabled between enumeration and its `getdns` read errors the whole observation ⇒ degrade+warn (conservative — no verdict from a torn view); a service enabled *after* enumeration is invisible to this pass ⇒ covered by S1's first cadence once the runtime is up (and by the first apply's own capture before that). The enumerate-then-read pattern is the same shape the rollback path already uses, so the race window is not new.

### S4-A2. Does `RestoreFromBackup` actually heal the widened evidence — can the observed loopback set outrun the backup entries? — RISK (restore-completeness hole; today's code has no post-restore verification)

`RestoreFromBackup` iterates **backup entries only** and deletes the backup on success (`macos_dns_sc_protect.rs:609-632`); nothing re-observes the services afterward. The design claims the restore "heals precisely the partially-pinned set" (design §3.2.3). That holds only when **observed-loopback ⊆ backup entries**. In the canonical crash-mid-pin scenario it does: the backup is written before the first mutation over exactly the enumerated set (`phase10.rs:4621-4630`), and the pin loop iterates that same set (`phase10.rs:4631-4641`), so residue ⊆ backup. But S4 *widens the trigger* to any observed loopback service, and the subset invariant is not maintained across apply sequences:

- Apply N enumerates {Wi-Fi, Ethernet}, pins Wi-Fi (loopback), crashes *before* finishing — backup has both entries. So far so good.
- The failure shape that breaks the invariant: apply N pins Wi-Fi; apply N+1 later re-enumerates **without Wi-Fi** (service disabled at that moment) — the backup is rebuilt from the current enumeration only (`phase10.rs:4607-4620` builds `backup_entries` fresh and `:4624-4630` overwrites the file), so Wi-Fi's entry is dropped; Wi-Fi is re-enabled (still loopback-pinned from apply N); crash. The guard now observes Wi-Fi `LoopbackOnly`, `backup_readable = true`, decides `RestoreFromBackup`, restores whatever entries exist — **Wi-Fi is not among them** — deletes the backup, reports success (`macos_dns_sc_protect.rs:632-635`), and the daemon starts with live loopback residue the guard just claimed to have healed. Silent open, post-fix.

This hole is *reachable today* in weaker form (scutil-primary loopback with the primary service absent from backup), but S4's premise — "every branch terminates in either healed or loudly-stranded; the silent-open branch is closed" (design §3.3) — is false without closing it, and S4 is the change that makes the guard *trust* per-service observation.

**Required mitigation (design amendment, pick one, fail-closed):**
(a) after a successful restore, re-run the per-service observation and fail loud (`FailLoudManualRestoreRequired` semantics naming the surviving services) if any service still classifies `LoopbackOnly`; or
(b) before restoring, verify observed-loopback ⊆ backup service names and take the `FailLoudManualRestoreRequired` branch (now armed with the observed list — which §3.2.3 already builds) when the check fails.
(a) is strictly stronger and reuses the new helper; (b) is cheaper. Either way §3.4 needs the regression test: `observed_loopback_service_missing_from_backup_fails_loud_not_silent_restore`.

### S4-A3. Can a legitimately loopback-pinned service be misclassified as residue, and is all-enabled-services scope the right justification? — RISK (availability/actionability, owner-ack required; fail-loud direction, not fail-open)

Constructed host: an operator runs their own local resolver (dnsmasq/unbound/Pi-hole-on-macOS) with services intentionally pinned to `127.0.0.1`, then installs RustyNet. First startup: guard observes `LoopbackOnly`, no protection running, **no readable backup** (RustyNet never ran here) → `FailLoudManualRestoreRequired` → startup refused (`daemon.rs:11589-11593` → `DaemonError::InvalidConfig`). Worse, the refusal message (`macos_dns_sc_protect.rs:526-536`) instructs the operator to run `networksetup -setdnsservers "<svc>" Empty` — i.e., destroy the intentional configuration to make the daemon start. Pre-S4, this host was invisible unless its pin reached the scutil primary; S4 makes the guard *actively refuse* on it.

The design's defense is the owner decree: under all-enabled-services scope (gap doc §5.2, design §3.3), an intentional loopback pin without running protection is residue "by definition," and the owner retains a config-exclusion escape hatch. That decree legitimately governs **pinning scope** (what the daemon may own while protecting). S4 extends the same set to govern **residue adjudication at startup**, where the daemon has never run and has no backup proving provenance — a harsher consequence (startup refusal) derived from a scope decision made for a different purpose. Note the direction is fail-closed/loud, never fail-open, and the message does name the backup path (an operator who knows their own config can recognize the false positive); so this is an availability and actionability risk with an owner-decree backstop, not a security break.

**Required mitigation:** the design (or its implementation change set) must state explicitly that S4 makes intentional-loopback hosts refuse startup, that the reserved config-exclusion hatch becomes load-bearing for this case, and get owner ack for that consequence. Cheap softening within the decree: when `backup_readable == false` AND no RustyNet state dir/marker exists, the message could note that a non-RustyNet origin is possible — without weakening the refusal.

Under-claim note: we found no evidence macOS itself transiently advertises loopback service DNS absent an explicit pin, so no second false-positive source is claimed.

### S4-A4. Does degrade-with-warning avoid stranding while never hiding real residue, and is S1 a sufficient backstop for the degraded window? — CONFIRMED-SAFE on direction; the design's window bound needs one precision fix

**No stranding:** refusing startup when observation is unavailable would strand every host whose helper is merely slow at guard time (the guard runs before key prep, `daemon.rs:11595`), with zero residue evidence in hand — `decide_startup_recovery`'s inputs would be fabricated. Degrading keeps today's scutil signal (`macos_dns_sc_protect.rs:556-563`) live and adds the loud warning: correct calibration, and it matches the owner decree that refusal is reserved for removal *confirmed necessary and impossible* (design §3.2.4).

**Does the degraded window actually close via S1's "≤ ~31 s" (design §3.2.5)? Precision fix required.** S1's assert requires `dns_protected == true` (`phase10.rs:4688-4692` early-fails otherwise) — i.e., a **completed** first apply. Walk the degraded-startup cases:
- Helper down at startup **and stays down**: the first apply fails at enumeration (`phase10.rs:4581-4583`) → reconcile ladder → `RestrictionMode::Permanent` within 5 consecutive failures. Loud, fail-closed — but the residue is *not* healed in ≤31 s; §3.2.5's bound does not hold on this path. The design's own §5.4 drill states the Permanent outcome; §3.2.5's blanket "≤ ~31 s" should be scoped to the helper-recovered case.
- Helper recovers: first apply runs. With a backup present, capture of loopback residue resolves the baseline from the prior backup (`phase10.rs:4584-4593`) and re-pins — healed, then S1 keeps it healed. **Without** a backup, the capture guard refuses the apply loudly (`resolve_backup_baseline_entry`, gap doc §7) — again loud, not silently healed.
So every branch ends healed or loud — the S4 safety claim survives — but the closed-form "≤ ~31 s after first healthy tick" is true only when the helper recovers *and* a readable backup exists. **Required mitigation (doc):** restate §3.2.5 as: helper-recovers+backup ⇒ healed ≤ ~31 s; otherwise ⇒ loud Permanent/loud apply-refusal, never silent. No code change implied.

**Hiding real residue:** degraded mode is exactly today's blindness plus a warning — a partial residue with an unpinned primary is missed until the first apply or S1. Accepted by design and correctly disclosed; nothing further demanded beyond the §3.2.5 precision.

### S4-A5. Is the second-instance-race claim sound? — CONFIRMED-SOUND for the steady state, with two recorded caveats (one is the S4-before-S1 interim)

The claim (design §3.2.6(i)): a second daemon instance's guard restoring SC DNS out from under a live protecting instance leaves a fail-closed window — the live instance's pf floor holds and its next apply re-pins, and S1 heals a mis-restore within one cadence. Verified sound in the steady state: the live instance's `dns_protected` stays true and the anchor stays rendered (`phase10.rs:4558`, `3451-3459`), so the restored real resolvers cannot resolve via :53; the live instance's next generation apply re-captures the restored (real, non-loopback) values as the baseline — `resolve_backup_baseline_entry` records non-loopback captures unchanged (`phase10.rs:4607-4620`) — and re-pins; with S1 landed, drift is detected ≤31 s and healed.

Caveat 1 (transitional, real): the "next apply re-pins" leg is weak **until S1 lands** — on a healthy converged node no generation apply ever fires (the very gap S1 closes), so in the S4-only interim the mis-restore persists until an unrelated membership/assignment event. The race window is fail-closed but *unbounded* in the interim. The S6→S4→S1 order (design §4.2) accepts this; record it so the interim is not mistaken for the composed end state.

Caveat 2 (chain stays loud): the guard's restore deletes the backup on success (`macos_dns_sc_protect.rs:632`) — the live instance's backup is destroyed out from under it. Harmless to the live instance (its next apply re-captures fresh), but a subsequent crash *before* that re-apply leaves residue with no backup → the guard's loud-refusal branch, not silence. Also unchanged from the adversarial review §4: whether single-instance locking makes the race unreachable was never verified; S4 does not change that, and this review does not re-litigate it — the design correctly prices the race as an unchanged residual.

## 3. The §4.2 file-ownership split against current code

Verified against this tree (HEAD `4bc3671e`; S6 landed `003dabc9`, S4/S1 not yet landed):

- **`macos_dns_sc_protect.rs` (S4 only):** accurate.
