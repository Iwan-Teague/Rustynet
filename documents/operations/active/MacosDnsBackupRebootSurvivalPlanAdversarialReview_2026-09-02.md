## B) Findings

### B.1 Who writes the backup, and is a daemon-writable backup an escalation? (attack 1)

**The writer is the daemon process itself, unprivileged.** `write_networksetup_dns_backup` (`macos_dns_sc_protect.rs:407-436`) is a plain in-process `std::fs` write + chmod 0600; the daemon runs as the dedicated `rustynetd` service account (plist `UserName`/`GroupName`, installer `:492-:494`). Today it can write inside `/private/var/run/rustynet` only because the root helper recreates that dir `root:0o770` per boot with the daemon's group admitted (installer `:533-536`, `:473` comment). Under Option A the backup lands beside `/usr/local/var/rustynet/rustynetd.state` — a directory created and owned by the same daemon (`daemon.rs:13527-13541`, `run_preflight_checks` create-dir block) — so the write trivially succeeds. The plan's §1.6 mechanics are correct.

**The privilege-escalation attack is real in shape and refuted in substance.** Shape: anyone who can write the backup controls what the **root** helper restores at next startup — the startup guard (`daemon.rs:11773` → `run_startup_dns_recovery:796`, restore arm `:840-868`) feeds each backup entry's servers straight into `networksetup -setdnsservers <svc> <servers>` through the privileged socket, and the helper validates only argv *shape*: `is_valid_networksetup_dns_server_list` (`macos_dns_sc_protect.rs:113-118`) accepts **any** non-empty list of parseable `IpAddr`s — attacker-controlled resolvers included. So daemon-uid write access to the backup = host-wide DNS redirection at next boot, executed by root.

Substance: **this grants the daemon nothing it does not already hold.** The same `validate_networksetup_args` allowlist admits `-setdnsservers <svc> <valid-IP-list>` from the daemon at *any* time — that is exactly how the apply path (`phase10.rs:4665-4676`) and teardown restore (`:4259-4274`) legitimately run. An attacker with the daemon's uid does not need to plant a backup file to set host DNS; it asks the helper directly, today, with no file involved. The backup therefore confers zero additional capability, and no helper-side validation of restored DNS *values* (beyond IP syntax) is needed or missing — *given the daemon's standing power*. The plan's §3 invariant-5 threat model, however, is written for the old path — "/var/run is root-owned, so planting a file there requires root — an attacker with root has already won" — and that sentence **becomes false under Option A**, where the document's directory is daemon-writable *by design*. The invariant must be restated for the durable path (amendment A2): the trust question was never "can the author set DNS" (the daemon always could) but "is the content the *right* pre-protection baseline" — a stale-content question, which the no-fallback-read and capture-guard rules already answer.

### B.2 Ordering and fail-closed on write failure (attack 2)

Confirmed, with one nuance the plan should record. In `apply_dns_protection` (`phase10.rs:4587`): enumeration → capture guard → baseline resolve → **backup write** (`:4657-4664`) → only then the per-service mutation loop (`:4665+`). A backup-write failure returns `DnsApplyFailed` before the first `networksetup -setdnsservers`, so the host is never mutated without a backup — fail-closed as the plan claims. Two verified nuances:

1. `self.dns_protected = true` is set at `:4588`, *before* the backup write, and deliberately stays true on a system-configuration failure (`:4606-4615` comment) because the pf DNS-block rules are already installed and reverting the flag would drop them on the next reconcile. So a backup-write failure leaves the node **pf-protected, SC-unmutated, prior backup intact** — protected and unstranded. Correct, but it is "abort protection-apply", not "abort protection"; the plan's invariant 2 wording ("a write failure aborts protection") should say precisely this.
2. A mid-apply `networksetup` failure (some services pinned, backup written) aborts with the durable backup readable — the rollback/startup-guard restore path can use it. This is the plan's own invariant-2 test; it holds, and moving the path does not touch the ordering.

### B.3 "Never read the volatile path as fallback" (attack 3)

Confirmed by exhaustive reference check: `NETWORKSETUP_DNS_BACKUP_PATH` appears at exactly `macos_dns_sc_protect.rs:770, :816, :830, :838, :847, :884, :909` (messages, startup read, restore, remove) and `phase10.rs:4257, :4629, :4661` (rollback read/remove, apply prior-read, apply write). No startup path consults `/private/var/run` (or any second candidate path); the reader takes one path argument with no fallback branch. The plan's §3 list of sites missed `:884`/`:909` (the post-restore `remove_networksetup_dns_backup` calls) — they must move too (amendment A1 folds them in).

### B.4 Reboot semantics: the durable dir survives, but the proving stage does not exist for macOS (attack 4 — the load-bearing refutation)

**The state dir survives reboot** — `/usr/local/var/rustynet` is on the durable volume, owned by the service account; the backup beside the state file inherits that. No dispute.

**But the plan's live-proof step is unachievable as written.** The plan §4 step 4 requires "a macOS run whose stage set includes the macOS reboot cell with DNS protection active across the reboot". The registry has no such cell: `live_reboot_recovery` (`live_lab_stage_registry.rs:2049-2052`) overrides only `name`, `logical`, and `enable: EnableRule::LinuxLiveSuite`, so it inherits `DEFAULT_SPEC`'s `platform_rule: PlatformRule::LinuxOnly` (`:485-506`) — Linux-only by *both* platform rule and enablement rule. Its implementing binary is `live_linux_reboot_recovery_test.rs` (687 lines; `grep -n "macos\|dns_protect\|networksetup"` returns nothing; usage block `:675-687` is exit/client SSH hosts + WireGuard checks). There is no macOS reboot implementation anywhere in the tree. The failure transcript in §1.1 of the plan was observed *because a lab reboot happened outside any stage* — the stage cannot currently prove the fix. Either a macOS reboot stage must be added (registry entry + implementation driving `networksetup` observation across a guest reboot), or the plan must name the focused proof it will actually accept. Amendment A3.

**cleanup_hosts does not wipe the durable backup — and that has a concrete consequence.** The macOS cleanup (`adapter/macos.rs:247` → `macos_traffic.rs:427-486`) stops the launchd job (`:430-432`), flushes pf anchors + utun (`MACOS_RESET_COMMAND`, `:113` — no `networksetup` anywhere), then removes an **explicit rm list** (`:466-483`): membership.\*, trust seeds/watermarks/assignments, `rustynetd.state`, `wireguard.key`. The QH-40 marker (`rustynetd.state.shutdown-residue.json`) is *already* not on that list, and a future `rustynetd.state.networksetup-dns.failclosed.bak` would not be either. Consequences, in order of severity:

1. **Bootstrap-strand by service drift (real).** cleanup kills the daemon mid-protection with no teardown → SC loopback persists (that is the plan's own premise) and the durable backup persists. Next run's `bootstrap_hosts` starts the daemon → guard sees residue + readable backup → attempts auto-restore. If the guest's service set changed between runs (renamed/removed service), the restore argv fails → the daemon **refuses to start** (`:868-875`, backup retained) → `bootstrap_hosts` fails the run with the strand error. Fail-closed, but a run-killer the lab will hit as soon as the durable backup starts surviving cleanups. The cleanup list must therefore add the derived backup path (and, honestly, the already-missed residue marker), or `assert_node_clean` must grow an SC-DNS probe (its current probe checks pf/process/utun only, `:489-493` doc + `MACOS_NODE_CLEAN_PROBE :139`). Amendment A4.
2. **Stale-restore across runs (benign but must be stated).** When service sets *do* match, the next run's daemon silently restores the previous run's recorded "operator DNS" before the new run's apply. That is the feature working, and the M1 capture guard (`phase10.rs:4624-4648` + `resolve_backup_baseline_entry`) makes a later re-apply re-capture correctly: prior entries win only for services whose **current** DNS is loopback, so a snapshot-reverted SC posture (plan §5.6) yields a fresh correct baseline and cannot have the stale backup "restore a wrong baseline". The plan's §5.4/§5.6 worry is closed by code — but the closure should be cited in the plan, not assumed.
3. **A durable backup surviving uninstall.** The installer creates the state root; nothing in the reviewed uninstall path (`rm` list above, installer) removes the derived file. Same class as (1); the same amendment covers it.

**Guard-vs-state-dir ordering (plan §5.1) — resolved, record it.** The startup DNS guard (`daemon.rs:11773`) runs **before** `run_preflight_checks` (`:11778` call → `:13527` def), which is where `create_dir_all(state_path.parent())` happens (`:13535`). This is safe for the reboot case (the durable dir already exists) and for the fresh-install case (missing dir reads as missing backup → `Ok(None)` → strand message — correct), and apply-time writes are covered by the writer's own `create_dir_all` (`:410-412`) plus preflight having run by then. The plan's open question closes in the safe direction; the plan should state the ordering fact rather than leave it as a question.

### B.5 Option C, the worst case, and one fail-open seam in the plan's own success path (attack 5)

**"Refuse to start + manual fix" is the strictest secure default; the plan's rejection of C stands.** Verified: `residue_evidence_from_observation` (S4) proves only "some enabled service is loopback-only" — nothing binds the posture to RustyNet authorship (`macos_dns_sc_protect.rs:505-512` doc; no signature/HMAC primitive exists anywhere on this path). `Empty` on unauthored residue is a data-loss action an attacker or third-party tool could induce (pin loopback, wait for reboot, daemon "helpfully" clears the operator's static DNS). The unattended-node counterargument (a DHCP-only guest's correct original *is* `Empty`; the manual fix is literally the command C would have run) costs automation, not correctness — and the durable backup removes most of that cost anyway. No amendment to the C rejection.

**But the plan's own §4 live-proof target — the `:913` "backup restore itself completed" path — contains a seam the refute pass must name.** In the `RestoreFromBackup` arm, when the post-restore observation is *unavailable*, the guard retires (removes) the backup, logs a warning, and returns `Ok` (`:905-917`). So: restore argvs reported success, verification could not run, and the only recovery document is deleted. If the sets did not actually take (SC reverted them, or a later actor re-pinned), the host is loopback-stranded at *next* start with no backup — strictly worse than the state C would create, arrived at by a path the plan treats as success. Narrow (networksetup is synchronous; argv-success-but-not-applied is rare), but it violates fail-closed: **an unverified restore must retain the backup**, not retire it. Amendment A5. The plan's §4 step 4 currently quotes this path as the acceptance outcome; it must instead require the *verified* clear (`survivors.is_empty()` branch, `:889-896`).

### B.6 The plan under-scopes the volatile-artifact set: the resolv.conf backup has a macOS branch too (attack 4/6 adjacent)

`linux_dns_protect.rs:248-254` defines `RESOLV_CONF_FAILCLOSED_BACKUP_PATH` for **linux `/run`** *and* **macOS `/private/var/run/rustynet/resolv.conf.failclosed.bak`** — and the macOS apply path writes it: `phase10.rs:4676-4695` (`DnsFailclosedFile` `RESOLV_APPLY`, explicitly *best-effort* on macOS, plus a second best-effort durable artifact `/etc/resolver/rustynet` at `:4701-4712`), restored best-effort at teardown (`:4779`). The plan's §1.7/§6 frames this constant as "the Linux twin" and scopes it out; that framing hides that **on macOS the same apply produces a second volatile backup plus one durable un-restored artifact**. Impact is bounded — the startup guard never reads the resolv backup, macOS regenerates `resolv.conf` from restored SC state, and `/etc/resolver/rustynet` is scoped to `*.rustynet` names — but "durable backup + guard = fully automatic recovery" is not the whole recovery story until the plan says so. Amendment A6 (scope statement, not a code demand).

### B.7 Live proof (attack 6)

Answered by §B.4: `live_reboot_recovery` exercises **Linux only** (`PlatformRule::LinuxOnly` default + `EnableRule::LinuxLiveSuite`), stops at nothing macOS, and its binary has no macOS DNS-protection code. It does not "stop protection before rebooting" — the question's premise fails earlier: it never touches macOS protection at all. The macOS reboot-with-protection scenario exists today only as the unplanned incident in plan §1.1. See amendment A3.

## V) Verdict

**READY-WITH-AMENDMENTS.** Option A is confirmed correct on every substantive attack: the write ordering is fail-closed, the no-fallback invariant holds in code today, the escalation attack reduces to power the daemon already holds, Option C's rejection is sound, and the QH-40 derivation pattern is the right vehicle. The plan text needs the amendments below before an implementer should touch the constant — A3 changes what "done" means.

### Fail-closed tests the implementation MUST write first

1. **Truth table preserved (path-agnostic):** `decide_startup_recovery(true, false, false) == FailLoudManualRestoreRequired`, `…(true, false, true) == RestoreFromBackup`, `…(true, true, _) == NoAction`, `…(false, _, _) == NoAction` — the existing `startup_guard_restores_from_readable_backup_only` (`:1243`) must pass unmodified against the derived-path plumbing.
2. **Present-but-unreadable durable backup is residue, not absence:** corrupt/truncated/foreign-schema document at the derived path → `read_networksetup_dns_backup` hard-`Err` → strand refusal, backup retained (reader semantics `:439-478` unchanged).
3. **No volatile fallback:** a valid backup planted at the old `/private/var/run` path is ignored by `run_startup_dns_recovery`; recovery decisions consult only the derived path (negative test pinning invariant 5).
4. **Derivation:** `networksetup_dns_backup_path(state_path)` is a sibling of the state file (`with_file_name`), moves with a `--state-root` override, and has the degenerate-path fallback `marker_path` has (`shutdown_residue.rs:182-192`); every `NETWORKSETUP_DNS_BACKUP_PATH` use site listed in A1 takes the derived value (a compile-time grep gate or a test that the const is gone — the bare const is deleted, not deprecated).
5. **Restore writes argv the helper admits:** for every backup entry shape (`None` → `Empty`; `Some(list)` → exact list), `startup_restore_argv_for_entry` output passes `validate_networksetup_args` (`privileged_helper.rs:2936`) — pins the backup→helper contract before any path moves.
6. **Unverified restore retains the backup (A5):** observation-unavailable after restore → backup still on disk + loud warn (this test pins the amended behavior, and fails until A5 is implemented).
7. **Cleanup compatibility (A4):** the macOS cleanup command list includes the derived backup path (or `assert_node_clean` includes an SC-DNS probe) — a stage-level test on `macos_traffic::cleanup_runtime_state`'s command set.
8. **Message pins:** `manual_restore_message_names_the_fix_per_service` (`:1267`) updated to the derived path; the `:830` no-socket, `:868` restore-failed, and `:875` retained-backup messages all interpolate the derived path (grep-gate: no remaining `NETWORKSETUP_DNS_BACKUP_PATH` identifier).
9. **Apply ordering preserved:** a mocked write failure before the first `networksetup` set aborts with the prior backup intact and zero mutation argvs issued (invariant 2, now against the derived path).
