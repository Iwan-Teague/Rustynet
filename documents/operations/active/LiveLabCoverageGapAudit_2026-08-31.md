# Live-Lab Coverage Gap Audit — 2026-08-31

**Type:** Coverage audit (doc-only). **Owner question:** "I'm sure there are gaps, scenarios we haven't verified we're protected against."

## 1. Purpose and scope

This document answers a question that the existing status documents do not ask. `LiveLabStageStatus_2026-08-14.md` tracks the per-OS pass/fail **status** of stages that already exist. This audit is **orthogonal** to that: it asks whether the live-lab suite is **comprehensive** — which threats, invariants, and failure modes have **no stage testing them at all** (MISSING), which stages assert **less than the invariant they claim** (WEAK), and which parts of the coverage *structure* make the suite answer the wrong question or hide failures (CHANGE).

Every finding below was checked against the prior gap-tracking documents (§4) so that already-tracked work is never re-reported as new. Statuses: **NEW** (not tracked anywhere), **TRACKED** (already owned elsewhere, listed only for completeness), **UNVERIFIED** (plausibly uncovered but this audit could not confirm because the relevant validator body was not read first-hand).

## 2. Method

1. **Inventory.** The stage catalog was read first-hand: `define_stage_catalog!` in `crates/rustynet-cli/src/vm_lab/orchestrator/stage/mod.rs:161–301` — 74 stages across suites (setup / live T0–T4 / soak / cross-network / chaos T4 / negative-control T5 / cleanup). For each stage, the audit used the catalog entry plus the validator-body descriptions recorded (with file:line citations) in the prior gap documents, not the stage names alone.
2. **Invariant sources.** `documents/SecurityMinimumBar.md` §3 Critical Controls (L13–255, read first-hand this session), §6 Required Test Evidence headings; `documents/Requirements.md`; the security-auditor skill's `references/attack-catalog.md` (10 attack classes) and `references/lab-playbooks.md` (10 playbooks); `CrossPlatformRoleParityPlan_2026-06-21.md` + `CrossPlatformRoleParityRefresh_2026-07-23.md` (role × OS live-proof mandate); `RustynetDataplaneExecutionPlan_2026-05-18.md`.
3. **Dedup.** Every candidate gap was cross-referenced against `LiveLabCoverageGapDiscovery_2026-08-19.md` (G1–G9), `LiveLabStageCoverageGapPlan_2026-08-10.md` (G1–G5, I1–I5), the QH items in `QualityHardeningTodo_2026-07-25.md`, `FullTodoInventory_2026-07-28.md`, and the parity ledgers, before being classified NEW.

The stage inventory itself (74 stage IDs, suites, tiers, and the one-line property each validator actually asserts, per the catalog and prior citations) is the audit baseline; it is not restated here. Findings that depend only on the inventory are marked TRACKED and pointed at their owning document.

## 3. Executive summary — the top gaps

Ranked by risk. **Release-blocking** = leaves a SecurityMinimumBar §2 blocking rule or the cross-platform parity mandate unprovable even if every existing stage passed.

1. **[BLOCKING, TRACKED] The adversarial suites never run.** Nine chaos stages (T4) and four negative-control stages (T5) exist — clock rollback, signed-state adversarial, membership adversarial, privileged-boundary, plus the fail-loud inversion controls — and have **zero** rows in the live `--node` ledger. The suite's entire anti-adversary half is unproven on the engine of record. Tracked: Discovery G2, Plan_08-10 G4 (dependency cascade, `stage/chaos.rs:48–50` + `orchestrator/runner.rs:32`), Change C-5. This is the largest single hole and the highest-leverage fix; it needs execution and repair, not new stages.
2. **[BLOCKING, NEW — M-1] Anchor control-plane fingerprint pinning is not enforced end-to-end**, so no stage could even assert the MITM defense. Server-side TLS landed (QH-26), but `rustynet-cli`'s bundle-pull/enroll clients do not pin the server fingerprint; the pin verifier exists only as a `#[cfg(test)]` pattern inside `rustynetd/src/anchor_tls.rs` (SecurityMinimumBar L105–114). The control is a design contract, not a tested fact.
3. **[HIGH, NEW — M-2] Enrollment one-time-credential race/replay is untested live.** §3.3 (L210–214) demands atomic, race-safe single consumption under concurrent requests; the only live stage (`live_enrollment_restart_validation`) tests a daemon restart mid-enrollment, not concurrency or post-redemption replay.
4. **[HIGH, NEW — M-3] Pin-rotation grace residual untested live.** A revoked former-owner key is still accepted while an Active owner co-signs (`membership.rs:1308–1346`; SecurityMinimumBar L155–174) — and the residual (compromised old key satisfying grace on a device that never received the new pin) has no adversarial stage anywhere.
5. **[HIGH, NEW — M-4, M-5, M-6]** Three §3 families have no live stage at all: audit-log tamper-evidence (§3.9), secrets-redaction breadth beyond daemon logs (§3.4, env/CLI/API/dumps), and the web/admin surface (RBAC denial, MFA, CSRF/cookie — §3.6–§3.7).
6. **[MEDIUM, UNVERIFIED — M-7, M-8, M-10, M-11]** Plausible seams where a stage exists but its scope probably does not reach the §3.8 clause: traversal hint replay, failover/failback ACL preservation, key-custody runtime permission downgrade, protocol-filter ACL in shared-exit scenarios. Each needs a one-time validator read before being accepted as a gap.
7. **[CHANGE, NEW — C-4, C-6]** Dead-code-shaped control inflates apparent transport coverage (`validate_negotiated_tls`, callers are its own unit tests); and only one stage (`security_audit_validation`) has recorded mutation evidence that it fails when its control is removed (Plan_08-10 I1) — the rest of the live suite is unproven against the QH-02 rule.

Sections 5–7 hold the full tables. The tracked baseline (what is already owned and where) is §4; do not re-file those.
