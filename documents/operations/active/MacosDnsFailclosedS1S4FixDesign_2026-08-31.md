## 0. Scope

This document designs exactly two fixes from the adversarial review:

- **S1** — macOS DNS posture drift on an otherwise healthy node is never re-detected after the initial apply: `assert_dns_protection` has no call site outside the apply path, and the reconcile loop's apply predicate has no DNS-posture disjunct.
- **S4** — a crash mid-pinning can leave partial System Configuration (SC) loopback residue that the startup-recovery guard cannot see, because the guard observes only the scutil primary resolver #1 and never the per-service `networksetup` state.

S6 (verifier hardening) is designed and landed separately and first; this document treats it as an external dependency and as the live acceptance oracle for S1/S4. Anything not S1/S4/S6-sequencing is out of scope.

## 1. Shared background (the M1 model this design extends)

The M1 model, owner-approved in the enforcement gap doc, is: while `protected_dns` is active, the daemon pins **every enabled hardware network service** to loopback resolvers via the privileged helper (`networksetup -setdnsservers <service> <loopback...>`), after writing a session-scoped backup of the pre-apply per-service DNS state to `/private/var/run/rustynet/networksetup-dns.failclosed.bak` (`NETWORKSETUP_DNS_BACKUP_PATH`). Scope = all enabled services, no VPN/utun special-casing (gap doc §5.2). The pf floor is independent of the SC posture: the interface-agnostic labeled `:53` block rules (`rustynet-dns-block-lan-{udp,tcp}`) are rendered whenever DNS protection is on (`phase10.rs:3451-3459`), so plaintext `:53` to non-loopback resolvers stays blocked even if SC posture drifts.

Owner decrees this design must respect:

1. Strictest-secure-practical = M1 **plus** reconcile-loop re-assertion (gap doc §5.1). S1 is the second half of that decree, not a new invention.
2. Scope is all enabled services (gap doc §5.2); a future config-based exclusion list is the owner's explicitly-reserved escape hatch, not part of this design.
3. Rollback ordering: restore SC DNS **before** any pf anchor reload (gap doc §10.7). Both fixes inherit this for free by reusing the existing apply/restore entry points rather than inventing new mutation paths.
4. Loopback-dead-port posture is intended while protected; residue is loopback pins observed while protection is **not** running.

## 2. S1 — DNS posture drift on a healthy node is never re-detected

### 2.1 Current behavior (exact, with citations)

- `assert_dns_protection` lives at `crates/rustynetd/src/phase10.rs:4687-4731`. It fails closed when `dns_protected` is false (`phase10.rs:4688-4692`), checks the rendered pf ruleset for the tunnel-scoped `:53` passes and egress handling via `ruleset_contains_dns_rule` (`phase10.rs:4693-4706`; implementation `phase10.rs:3717-3750`), then enumerates enabled services and asserts each still pins **some** DNS server (`phase10.rs:4719-4723`) and that the pinned list is loopback-only via `is_loopback_dns_server_list` (`phase10.rs:4724-4728`).
- Its only call sites are inside the apply path: `apply_generation_stages` at `phase10.rs:6766-6770` (right after `apply_dns_protection`, before pushing `StageMarker::DnsApplied`) and the inline regular-exit apply inside `apply_nat_forwarding` at `phase10.rs:4501-4508`. There is **no** periodic or event-driven call site anywhere in the daemon.
- The reconcile loop decides whether to run a generation apply from `will_apply_generation` at `crates/rustynetd/src/daemon.rs:10329-10333`: `DataplaneState::FailClosed || RestrictionMode::Recoverable || assignment_changed || membership_changed || local_route_reconcile_pending`. **None of the five disjuncts is a DNS-posture signal.** On a converged healthy node all five are false, so the apply block (`daemon.rs:10348-10350`, applying at `daemon.rs:10453-10480` with `protected_dns: true` at `daemon.rs:10464`) never runs, and DNS posture is never re-observed.
- The tick is 1 s (`DEFAULT_RECONCILE_INTERVAL_MS`, `daemon.rs:484`), with a 5-failure permanent-escalation cap (`DEFAULT_MAX_RECONCILE_FAILURES`, `daemon.rs:522`) — but that ladder only feeds from apply/pre-check failures, never from posture observation.
- The stale comment is in the M1 comment block of `apply_dns_protection` at `phase10.rs:4578-4580`: it claims that "the reconcile loop's assert_dns_protection keeps surfacing the drift." That is false today — the reconcile loop contains no such call. The comment must be rewritten as part of S1 so the code and the contract agree.
- Exposure window: unbounded. A service hot-plugged after apply (new Wi-Fi/hardware service, a VPN client or user action writing DNS via System Settings) acquires a non-loopback resolver and nothing ever notices until the next full apply, which a healthy node never performs. The review's confirmed-weaknesses summary names this precisely: drift never re-detected, bounded leak, unbounded window (review §8).
- What bounds the actual leak while drifted: the pf floor. Plaintext `:53` to non-loopback is dropped by the interface-agnostic labeled block regardless of SC posture (`phase10.rs:3451-3459`), and the floor stays rendered because `dns_protected` remains true. The live exposure is therefore posture divergence, not plaintext DNS: non-`:53` resolver channels (DoH to allowed endpoints — the endpoint pass rules at `phase10.rs:3496-3505` have no `:53`-style exclusion, noted as a hardening item in the review; mDNS `:5353`, explicitly out of scope in the review), cached resolver answers already delivered before the drift, and — most damaging operationally — **oracle divergence**: the S6-hardened live `DnsFailclosed` stage checks per-service `networksetup` state, so a drifted node reports RED in the lab while the daemon reports itself healthy.

### 2.2 Proposed fix mechanism

**Shape: a periodic, cadence-gated posture re-assert on the reconcile loop that, on drift, schedules exactly one heal through the existing full apply path; only a *failed heal* enters the existing reconcile failure ladder.**

1. **New cadence constant** in `daemon.rs`, placed beside its two precedents: `DEFAULT_DNS_POSTURE_ASSERT_INTERVAL_SECS: u64 = 30`. The two precedents are deliberate:
   - QH-54's `HOST_FIREWALL_ADMISSION_ASSERT_INTERVAL_SECS = 30` (`daemon.rs:486-497`) establishes that a *privileged* re-assert must ride its own 30 s cadence, **not** the 1 s reconcile tick — the DNS re-assert is likewise a privileged round trip (pf ruleset read + service enumeration + per-service `getdns`), and per-second would be prohibitive.
   - QH-39's `STATE_SNAPSHOT_HEARTBEAT_INTERVAL_SECS = 30` (`daemon.rs:499-521`) establishes the exact structural gap S1 fills: a healthy converged node performs no periodic action because none of the five `will_apply_generation` disjuncts holds. 30 s also leaves the lab's stage timeouts comfortable margin, mirroring the QH-39 rationale.
2. **New daemon field** `dns_posture_reassert_pending: bool` (alongside `local_route_reconcile_pending`, declared at `daemon.rs:4647`), initialized false, acting as the drift signal.
3. **Where the assert runs — the branch structure is normative:** the assert lives in the **`else` arm of the exact `if` at `daemon.rs:10348-10351`**, keyed on the *same re-read* of `will_apply_generation` that conditions the apply block. It is **not** a tail call beside `maybe_reassert_host_firewall_admission` (`daemon.rs:10601`), which deliberately runs after *every* pass. The re-read is load-bearing: the QH-04 traversal refresh between the first predicate read (`daemon.rs:10329-10334`) and the branch condition can itself flip `controller.state()` to `FailClosed` or `restriction_mode` to `Recoverable` mid-pass, so only the `else` arm makes the apply and assert branches mutually exclusive within a pass. Note there is **no `else` arm today** — the apply block ends at `daemon.rs:10599` and the tail (`daemon.rs:10601-10606`) runs unconditionally — so this is new structure, not a reuse of an existing exclusion. Within that arm, the assert is gated on:
   - the cadence timer having elapsed since the last posture assert. **Normative: the cadence timestamp advances on attempt, not on success.** If it advanced only on success, a persistently-failing assert would re-fire every 1 s tick — privileged hammering plus per-tick `last_reconcile_error` churn. This matches QH-54's set-before-call pattern (`daemon.rs:10642`) and is pinned by §2.4 test 2;
   - the node being otherwise healthy: `controller.state() != DataplaneState::FailClosed` and `restriction_mode == RestrictionMode::None` — a restricted or fail-closed node is already inside the apply/retry machinery and must not have its failure accounting polluted by observation noise. (The variant is `RestrictionMode::None`; the enum is `None | Recoverable | Permanent`, and the healthy state is set at `daemon.rs:10557` as `RestrictionMode::None` — there is no `Normal` variant.);
   - DNS protection actually being active (via the new public `dns_protected()` accessor on `Phase10Controller` — see §4.2; `assert_dns_protection` itself also early-fails on `!dns_protected`, `phase10.rs:4688-4692`, so the call site double-checks to avoid generating phantom drift on Linux or unprotected nodes).
   The macOS-only guard is the existing `#[cfg(target_os = "macos")]` convention already used by the apply path and the startup guard; the accessor returns false off-macOS so the gate naturally skips (matching §2.4 test 1).
4. **What the assert calls:** the existing `assert_dns_protection` (`phase10.rs:4687-4731`) unchanged. It already performs exactly the required observation — pf ruleset presence + per-service SC posture — and already returns a drift error naming the offending service and its servers (`phase10.rs:4719-4728`). S1 adds **no new observation code**; it adds only the scheduling around the existing assertion. This is the single hardened execution path rule applied to S1: no second, divergent DNS check is introduced.
5. **On drift (assert returns Err):** set `dns_posture_reassert_pending = true`, record the drift reason in `last_reconcile_error` (dedup pattern as at `daemon.rs:10299-10302`), and log loudly. **Do not** bump `reconcile_failures` and **do not** restrict here — detection is not failure. The next tick's `will_apply_generation` computation (`daemon.rs:10329-10333`) gains one disjunct: `|| self.dns_posture_reassert_pending`. The apply block then runs the full `apply_dataplane_generation` (`daemon.rs:10453-10480`), which re-enters `apply_dns_protection` (`phase10.rs:4557-4685`) and re-pins **every** enabled service through the hardened, backup-respecting, argv-allowlisted path — including re-capturing baselines correctly for the drifted service (a user's manually-set non-loopback DNS becomes the recorded rollback baseline, then is re-pinned to loopback, consistent with `resolve_backup_baseline_entry` semantics at `phase10.rs:4607-4620`). Because the heal reuses the full apply, the §10.7 ordering decree (SC restore before pf reload) and the stage-marker/audit structure are inherited, not reimplemented.
6. **On heal success:** the apply success path clears the signal (`dns_posture_reassert_pending = false` next to `pending_generation_apply = false` at `daemon.rs:10483`) and the posture assert cadence restarts.
7. **On heal failure:** the apply failure flows into the **existing** ladder unchanged — `reconcile_failures` bump, `last_reconcile_error`, `restrict_recoverable` (sets `RestrictionMode::Recoverable`, `daemon.rs:10769`), `force_fail_closed_or_restrict`, and `promote_to_permanent_if_over_limit` after `DEFAULT_MAX_RECONCILE_FAILURES = 5` (`daemon.rs:10280-10287` is the canonical pattern every apply pre-check failure already follows, e.g. `daemon.rs:10380-10389`). `RestrictionMode::Recoverable` itself forces `will_apply_generation` true (`daemon.rs:10330`), so a persistently failing heal keeps retrying until the permanent cap.
8. **Stale comment:** rewrite `phase10.rs:4578-4580` to state the real contract: the apply path asserts once at apply time; drift on a healthy node is surfaced by the periodic posture re-assert (30 s cadence, `DEFAULT_DNS_POSTURE_ASSERT_INTERVAL_SECS`) which schedules exactly one re-apply via `dns_posture_reassert_pending`; a failed heal escalates through the standard restriction ladder. No claim about the reconcile loop may appear that the reconcile loop does not satisfy — this comment was the original S1 trap.

**Explicitly rejected alternative — event-driven re-assert via SCDynamicStore change notifications:** the review offers "periodic or SCDynamicStore-change-triggered." This design chooses periodic-only. Rationale: an SCDynamicStore watch is a new async event-source in the daemon runtime, a new platform API surface, new failure modes (missed events, callback-thread coupling to the reconcile state machine), and substantially harder deterministic unit testing; the periodic assert bounds the drift window at 30 s + 1 tick, which is operationally equivalent for a posture whose worst-case leak is pf-bounded, and it follows two shipped precedents (QH-54, QH-39) instead of inventing new machinery. A change-triggered fast path can be layered later behind the same `dns_posture_reassert_pending` signal without re-design.

### 2.3 Failure-mode analysis (fail-open vs fail-closed)

**The fail-open/closed crux is the drift *response*, and it has three candidate answers:** (a) warn only — fail-open, rejected; (b) re-pin directly from the assert site — heal outside the hardened apply path, rejected (bypasses backup semantics, stage markers, audit, and the §10.7 ordering decree; violates one-execution-path); (c) schedule one full re-apply, escalating only on failed heal — **chosen**.

- **Why not immediate FailClosed on detection:** tearing the tunnel does not heal SC posture — only re-pinning does — and the actual leak while drifted is bounded by the pf floor (`phase10.rs:3451-3459`), which stays rendered. FailClosed on detection would convert a 30 s self-healing blip into a user-visible outage for a defect whose plaintext exposure is already zero. Proportionality, not leniency: the node is never left unprotected, because the protection state (`dns_protected`) and the pf floor persist through the entire heal cycle; what the ladder guarantees is that a *persistent* failure to heal lands in `RestrictionMode::Permanent` within 5 attempts (~5-6 s of ticks once the heal starts failing, bounded by the 1 s tick at `daemon.rs:484`).
- **Churn / fighting legitimate changes:** under M1, while `protected_dns` is active the daemon *owns* SC DNS for all enabled services (gap doc §5.2) — a manual SC edit during protection is by definition drift, and re-pinning it is the owner-approved contract, not misbehavior. The design bounds the fight to **one** full re-apply per drift episode: the signal is a latch cleared only by a successful apply, not a per-tick re-pin trigger, and the assert does not re-fire while the heal is pending (the apply block branch and the assert branch are mutually exclusive within a pass). The user's edited DNS is preserved as the rollback baseline by `resolve_backup_baseline_entry` (`phase10.rs:4607-4620`), so nothing is silently destroyed — it is re-pinned and recorded. The 30 s cadence keeps the steady-state privileged cost at one enumeration + N `getdns` round trips per 30 s, the same order as the accepted QH-54 firewalld assert.
- **Residual fail-open windows, stated honestly:** (i) up to ~31 s of divergence between drift and detection (cadence + tick) — accepted because the leak is pf-bounded and the divergence is posture, not traffic; (ii) if the privileged helper dies *and stays* dead, the heal fails and the ladder walks the node to `RestrictionMode::Permanent` — that is fail-closed escalation, but the drifted SC posture itself is only repaired by the operator (or the startup guard on next boot); the daemon never silently pretends health, because `last_reconcile_error` and the restriction mode surface the state.
- **Post-Permanent retry rate, disclosed by design:** after promotion to `RestrictionMode::Permanent` the heal retry continues at the 1 s tick rate — by design (fail-closed, operator-visible via the QH-55 recording of new failures), **not a regression** to be "fixed". The 5-strike cap ("within 5 attempts, ~5-6 s of ticks once the heal starts failing", above) bounds how fast the node escalates; it does not bound the retry rate afterward. A retry backoff would be a separate change under the one-execution-path rule, never smuggled into S1.
- **Assert scope, disclosed:** the assert's pf half validates the **rendered** ruleset (`render_pf_rules`, `phase10.rs:4693-4706`), not the live pf anchor. S1 therefore re-detects SC posture drift and renderer drift, but not an externally-flushed anchor on a healthy node (boot-time `pfctl -F` is fine — the next apply re-renders); live-anchor detection stays with S6's stage and the next generation apply. The "the pf floor bounds the leak" argument above presumes the anchor is live.
- **Net:** detection cannot fail open (it always schedules a heal), healing cannot fail open (failure escalates restrict→permanent), and the only "open" thing remaining during the window is posture advertising, which the pf floor covers for the `:53` path.

### 2.4 Mandatory unit tests (S1)

All daemon-side tests use the existing daemon test harness (fake controller/clock), phase10-side tests are pure:

1. `dns_posture_assert_skipped_when_not_dns_protected` — no drift signal, no assert call, on a node whose last apply did not enable protection (guards Linux/phantom-drift noise).
2. `dns_posture_assert_skipped_before_cadence_elapsed` — with the timer under 30 s, no assert; at/after 30 s, exactly one assert (fake clock). Also pins that the cadence timestamp advances on a failed **attempt**: a persistently-failing assert re-fires no sooner than 30 s later, never every tick.
3. `dns_posture_assert_skipped_while_restricted_or_fail_closed` — no observation noise enters failure accounting from a node already in `Recoverable`/`FailClosed`/`Permanent`.
4. `dns_posture_drift_schedules_single_reapply` — assert failure sets `dns_posture_reassert_pending`, does NOT bump `reconcile_failures`, does NOT restrict; next tick's `will_apply_generation` is true; apply runs with `protected_dns: true`; success clears the signal and `pending_generation_apply`.
5. `dns_posture_heal_failure_follows_reconcile_ladder` — simulated apply failure after drift: `reconcile_failures` increments, `restrict_recoverable` fires, five consecutive failures promote to `RestrictionMode::Permanent` (mirrors the existing ladder tests' shape).
6. `dns_posture_drift_clears_after_successful_apply_even_if_next_assert_fails_again` — a flapping service produces repeated single-apply heals, never an immediate double-apply within one pass (mutex of assert/apply branches).
7. phase10-level: `assert_dns_protection_drift_error_names_service_and_servers` already exists in behavior (`phase10.rs:4719-4728`) — keep it green and, if it is not currently a named test, pin it, because S1's daemon logic consumes exactly this error.
8. `dns_posture_assert_not_run_when_traversal_refresh_fails_closed_mid_pass` — the QH-04 traversal refresh flips `controller.state()` to `FailClosed` between the first `will_apply_generation` read and the branch re-read: the apply block runs AND the assert does **not** (mutual exclusion via the `else` arm of the `if` at `daemon.rs:10348-10351`, §2.2 item 3), and no observation noise enters the failure accounting.

Acceptance oracle for the whole fix: the live `DnsFailclosed` stage (S6-hardened, §5 below) on a macOS node, plus the drift-injection drill in §5.

## 3. S4 — Startup guard blind to partial SC loopback residue

> **Status: S4 is IMPLEMENTED and merged (commit `7675deea`).** The subsections below have been amended in place per the adversarial review (`MacosDnsFailclosedS1S4DesignAdversarialReview_2026-08-31.md` §6) to record the implemented behavior: the all-or-nothing observation rule (§3.2 item 1) and the post-restore completeness re-observation (§3.2 item 3) are implemented and tested.

### 3.1 Current behavior (exact, with citations)

- The startup-recovery guard runs inside daemon startup validation at `crates/rustynetd/src/daemon.rs:11587-11594`: a `#[cfg(target_os = "macos")]` block calls `run_startup_dns_recovery(...)` and maps any error to `DaemonError::InvalidConfig`, refusing startup. Its rationale comment (`daemon.rs:11577-11586`): SC DNS persists across reboot (unlike pf anchors), the guard runs before any protection is applied in this process, so loopback SC DNS observed here is residue; residue is removable, so refusal is reserved for when removal is impossible.
- Position: after `validate_daemon_config` (`daemon.rs:11545`) and the QH-40 shutdown-residue report-only scan (`daemon.rs:11567-11576`), before `prepare_runtime_wireguard_key` (`daemon.rs:11595`).
- The decision function `decide_startup_recovery(sc_dns_is_loopback, dns_protection_running, backup_readable)` is pure and complete over its three booleans (`crates/rustynetd/src/macos_dns_sc_protect.rs:508-521`; enum at `:477-489`): `!sc_dns_is_loopback || dns_protection_running → NoAction`; else `backup_readable → RestoreFromBackup`, else `FailLoudManualRestoreRequired`.
- **The observation gap:** `run_startup_dns_recovery` (`macos_dns_sc_protect.rs:549-639`) derives `sc_dns_is_loopback` solely from `read_scutil_dns` → `parse_scutil_primary_resolver_nameservers`, i.e. scutil's **unscoped primary resolver #1 only** (`macos_dns_sc_protect.rs:556-563`; the parser itself is `crates/rustynetd/src/macos_dns_failclosed.rs:145-175`, which collects only resolver #1's nameservers and skips everything after the scoped-queries section marker). scutil returning nothing is treated as `false` — "no residue evidence" (`macos_dns_sc_protect.rs:560-562`). `dns_protection_running` is hardcoded `false` at the call site (`macos_dns_sc_protect.rs:566`), correct for a pre-apply startup context.
- **The S4 scenario:** the apply pin loop pins services in enumeration order (`phase10.rs:4631-4641`), and enumeration order does not guarantee the scutil primary service is first (review §4). A crash after pinning services 1..k of n leaves services 1..k pinned loopback while the primary may still advertise its real resolver. On next startup: if the primary happens to be pinned, the guard sees loopback and restores/fails-loud correctly; if the primary is **not** among the pinned (or scutil reports nothing), the guard sees "no loopback" → `NoAction` → daemon starts. Self-healing then depends entirely on the first apply completing: if it completes, all services are re-pinned and the residue vanishes; if it **cannot** complete (privileged helper unavailable, apply precondition failure), the partial residue persists invisibly — the guard is the component designed to catch exactly this, and it cannot see it.
- Note the backup still exists in the crash scenario (it is written before the first mutation, `phase10.rs:4621-4630`), so when the guard *does* see loopback, `RestoreFromBackup` heals all recorded entries (`macos_dns_sc_protect.rs:587-637`, restore loop `:609-631`). The blindness is purely observational: the guard never asks the per-service state.

### 3.2 Proposed fix mechanism

**Shape: widen the guard's observation from "scutil primary #1" to "scutil primary #1 OR any enabled service pinned loopback-only," via a new observation helper in `macos_dns_sc_protect.rs`; keep the pure decision function's three-boolean truth table by feeding it an OR-ed residue-evidence bit.**

1. **New observation helper** in `macos_dns_sc_protect.rs` (same module that already owns the service-list parser, the `getdns` parser, the argv builders, and the privileged client usage — see its test inventory at `:641-991`): enumerate enabled services and read each service's DNS via the helper client, exactly the observation shape the rollback no-backup stranded path already performs in `phase10.rs:4271-4294` (enumerate + per-service read + `is_loopback_dns_server_list` classification), but implemented inside `macos_dns_sc_protect.rs` over `PrivilegedCommandClient` (the same client the restore branch already constructs at `macos_dns_sc_protect.rs:605-608`) so the module stays self-contained and no phase10 execution path is reused across the startup/apply boundary. Classification per service: `None` (no servers), `LoopbackOnly`, `NonLoopback`. The helper returns either `Observed(classification)` or `ObservationUnavailable(reason)`. **All-or-nothing rule (normative; SATISFIED and tested):** any enumeration or per-service `getdns` error fails the WHOLE observation into `ObservationUnavailable(reason)` — a partial observation is never returned. `observe_service_dns_postures_with` returns `ObservationUnavailable` on the first per-service error, never a partial `Observed`; this is pinned by `observation_unavailable_on_any_per_service_error` (§3.4). The rule is load-bearing: a best-effort partial view could classify an errored service as not-loopback-by-absence and report `Observed` over exactly the residue S4 exists to find.
2. **Residue evidence becomes:** `sc_dns_is_loopback` (existing scutil signal, unchanged, `macos_dns_sc_protect.rs:556-563`) **OR** any observed service classified `LoopbackOnly`. `decide_startup_recovery` keeps its exact signature shape and truth table (`macos_dns_sc_protect.rs:508-521`); only the meaning of its first argument widens to `residue_evidence`. All four existing decision tests (`macos_dns_sc_protect.rs:962`, `:967`, `:972`, `:977`) remain valid and green.
3. **Recovery semantics are unchanged and already correct for partial residue:** with residue evidence and a readable backup (the crash-mid-pin case — backup exists per `phase10.rs:4621-4630`), `RestoreFromBackup` iterates the recorded entries and empties/restores each (`macos_dns_sc_protect.rs:609-631`), which heals precisely the partially-pinned set. With residue evidence and no readable backup, `FailLoudManualRestoreRequired` — and the manual-fix message should now be fed from the **observed** loopback-pinned service list (the message builder `startup_recovery_manual_restore_message(&[String])` at `macos_dns_sc_protect.rs:526-536` already takes a service list; today the FailLoud branch derives the list from backup entries at `:569-574` and has no list at all when the backup is absent/corrupt, `:575-583` — with per-service observation there is always a concrete list to name). This makes the loud refusal actionable in exactly the case that was previously blind. **Restore completeness (S4-A2; IMPLEMENTED):** the restore loop iterates backup entries only, so the observed loopback set can outrun the backup (a later apply re-enumerates without a pinned service, dropping its backup entry; that service re-pins and a crash leaves residue the restore would silently miss). `run_startup_dns_recovery` therefore **re-observes per-service DNS after the backup restore**: if the re-observation is `Observed` and any service still classifies `LoopbackOnly`, the guard fails loud (`Err`) naming the surviving services and **retains the backup**; if `Observed` and clean, it removes the backup and returns `Ok`; if `ObservationUnavailable`, it removes the backup, emits a loud warning, and returns `Ok` (degrade-not-strand — a restored host is never stranded on an unobservable posture). Survivor classification is the pure helper `surviving_loopback_services`. The regression test is `observed_loopback_service_missing_from_backup_fails_loud_not_silent_restore` (§3.4).
4. **Observation-unavailable policy (the strand-vs-leak calibration):** if the helper socket is absent or the observation round trips fail, the guard **degrades rather than strands**: it proceeds with the scutil-only signal (today's behavior) but emits a loud startup warning naming the blind spot ("per-service DNS observation unavailable; partial SC residue may be missed until first apply"). Refusing startup here would strand every host whose helper is merely slow to accept connections at guard time (the guard runs before key prep, `daemon.rs:11595`), for a posture the runtime heals automatically — see the next point. This matches the owner decree verbatim: refusal is reserved for when removal is *confirmed necessary and impossible*; an unobservable posture is neither confirmed nor impossible.
5. **Defense in depth with S1:** the degraded startup path is closed by S1's runtime net. Once the daemon is up, the 30 s posture assert observes the same per-service state (`phase10.rs:4707-4729`); any residue the guard missed is detected within one cadence and healed through one re-apply. If the helper is truly broken, the heal fails and the reconcile ladder walks the node to `RestrictionMode::Permanent` — a loud, fail-closed terminal posture. **Scoped bound (per the review's S4-A4):** the "residue bounded to ≤ ~31 s after first healthy tick" figure holds **only when the helper recovers AND a readable backup exists** — S1's assert requires a completed first apply, which re-pins from the prior backup's baseline. The dead-helper path ends in loud `RestrictionMode::Permanent`; the no-readable-backup path ends in a loud apply refusal (the capture guard refuses the apply). Every branch terminates healed or loud — never silent — but only the helper-recovers-with-backup branch is bounded by ~31 s. No code change is implied by this scoping. The residue can no longer persist invisibly, which is the defect S4 names.
6. **Unchanged residuals, recorded:** (i) the second-instance race — a guard restoring SC DNS out from under a concurrently-running second daemon instance; the window is fail-closed (the live instance's pf floor holds and its next apply re-pins, and S1's re-assert heals a mis-restore within one cadence) and S4 does not change it; (ii) scutil-None as a *standalone* signal remains "no evidence" for the scutil half, but with per-service observation it no longer gates the whole guard — an observed `LoopbackOnly` service alone triggers recovery even when scutil reports nothing.

### 3.3 Failure-mode analysis (fail-open vs fail-closed)

- **Leak direction (the bug being fixed):** today a partial residue with an unpinned primary fails **open** — the guard says "nothing to do" while loopback pins sit on non-primary services with no running protection. The fix converts that to fail-closed: any observed loopback pin without running protection is residue, by the owner's definition (loopback-dead-port is intended *only* under protection, gap doc §5.4), and triggers restore or loud refusal.
- **Strand direction (the risk the fix must not create):** the obvious over-tightening is "observation failed → refuse startup." Rejected per §3.2(4): it strands hosts on a transient helper condition, and the refusal would be unactionable (there is no evidence residue exists). The strand-vs-leak tradeoff from the enforcement doc resolves to: degrade with a loud warning where evidence is absent, act where evidence is present, and let S1's runtime net close the degraded window.
- **False-positive direction:** could a loopback pin observed at startup be *legitimate*? Only if some other software intentionally pinned loopback DNS on this host while RustyDNS was not protecting — under the owner's all-enabled-services scope decision (gap doc §5.2) this is by definition RustyDNS residue; the owner retains the config-exclusion escape hatch if a real coexistence case appears. No silent carve-out is added by this design.
- **Intentional-loopback strand (owner-ack required, per review S4-A3):** S4 makes a host with non-RustyNet *intentional* loopback pins (e.g. a self-hosted dnsmasq/unbound/Pi-hole resolver) **refuse startup**: no protection running and no readable backup ⇒ `FailLoudManualRestoreRequired`, and the refusal message instructs the operator to run `networksetup -setdnsservers "<svc>" Empty` — i.e. destroy the intentional configuration to start the daemon. The direction is fail-closed/loud, never fail-open, but the consequence is an availability/actionability trade that **needs owner acknowledgement**; the owner's reserved config-exclusion hatch is the remedy for a genuine coexistence case. A softer message when no RustyNet state dir/marker exists at all (noting a non-RustyNet origin is possible) is permitted without weakening the refusal.
- **Persistence boundary:** the residue can only persist when the daemon starts but cannot complete its first apply — and that condition itself drives the reconcile failure ladder to `Permanent`, which is the loud fail-closed terminal. After a clean shutdown there is no residue at all (CleanShutdown intent rolls back, review §4); after a crash with a surviving backup, the widened guard restores; after a crash with no backup and observed residue, the guard refuses loudly naming the exact services and the manual command (`macos_dns_sc_protect.rs:526-536`). Every branch terminates in either healed or loudly-stranded; the silent-open branch is closed — and, with the post-restore re-observation implemented (§3.2 item 3), it is now **actually** closed even on the backup-outruns-observation sequence the review constructed (an observed loopback service absent from the backup entries no longer restores, deletes the backup, and reports success over live residue; §3.2 item 3).
