# macOS Helper Shutdown Ordering Implementation Plan — Adversarial Review (2026-09-02)

Adversarial refute pass against [`MacosHelperShutdownOrderingImplementationPlan_2026-09-02.md`](./MacosHelperShutdownOrderingImplementationPlan_2026-09-02.md), required by that plan's §6 ("Required adversarial refute pass") and executed against the real tree, not the plan's own text. Every claim below cites a file:line verified on this worktree; the command used for each anchor group is listed in §6.

Scope of the attack: (1) lease liveness — what actually holds the lease and what happens on daemon SIGKILL; (2) lease as a DoS lever from an unprivileged local process; (3) whether the lease changes *when* the helper stops under launchd `bootout`/`kickstart`, and whether the plan's bounds fit the plist's exit ceiling; (4) whether Option B's retry-with-deadline pushes the *daemon* past its own SIGKILL mid-rollback; (5) whether any plan path clears or suppresses the QH-40 residue marker; (6) whether the plan's live evidence distinguishes the fix from a lucky race, and what a deterministic test looks like.

---

## 0) Verdict

**READY-WITH-AMENDMENTS.** The lease design's security posture survives the attack: the lease holds no new privileged operation, is unforgeable by any peer the helper already rejects, and cannot outlive launchd's SIGKILL under any renewal pattern. The residue-marker invariant holds. But the plan has one load-bearing evidentiary hole (F1: the observed failure may not be the race the lease fixes), one design-doc compliance gap (F2/F3: the sign-off gate and the §3.3 caveat are silently dropped), one materially incomplete anchor (F4: `MACOS_LAUNCHD_STOP_COMMAND` already contains most of the M2 repair, and what remains is a deletion, not a reorder), and one real budget defect in Option B (F6). All are amendable without changing the chosen architecture.

---

## 1) F1 — The plan's primary fix may not address the observed failure (Q-1 is not "open", it is dispositive)

The plan's §1 narrative places the helper bootout "in the same back-to-back `;`-chain as the daemon bootout" and treats the 2026-09-02 failure as the same-stop completion race. But the adapter anchor the plan itself cites does not touch the helper at all:

- `restart_daemon` / `stop_daemon` (`crates/rustynet-cli/src/vm_lab/orchestrator/adapter/macos_install.rs:484-494`): `stop_daemon` runs only `launchctl bootout system/com.rustynet.daemon`; the adapter has no helper bootstrap, kickstart, or bootout anywhere (grep of `crates/rustynet-cli/src/vm_lab/orchestrator/adapter/` for `privileged-helper` matches only comments and the `MACOS_LAUNCHD_STOP_COMMAND` constant inside `macos_traffic.rs:18,42,49-50,58`).
- The plan's §6 Q-1 admits the failing run's exact stop sub-path is unconfirmed, then asserts "the narrative in §1 holds under either answer." **That assertion is false for the lease.** The two answers have different fixability:

  - *Answer (a) — the failure occurred at a traffic-adapter stop where `MACOS_LAUNCHD_STOP_COMMAND` (`macos_traffic.rs:46-78`) chained daemon bootout (`:47-48`) and helper bootout (`:49-50`) back-to-back.* This is the same-stop race. The lease fixes it: the daemon, SIGTERM'd first, acquires the lease from the still-alive helper in the microseconds before the helper's own SIGTERM; the helper defers exit for the defer budget; rollback dials a live socket.
  - *Answer (b) — the failure occurred at a later `enforce_baseline_runtime` daemon restart, with the helper job already removed by an earlier `MACOS_LAUNCHD_STOP_COMMAND`.* This is the path `restart_daemon` actually exercises, and it is the path the plan's own §5 proof stage runs. Here the lease cannot help and cannot even engage: there is no SIGTERM-deferral race because nobody SIGTERMs the helper at enforce time — the helper *job* was `bootout`ed earlier, and a bootout removes the job from launchd entirely, so KeepAlive (`Install-RustyNetMacosService.sh:580`) has nothing to respawn. The daemon's rollback dials a socket whose listener is gone; acquire fails (connect refused); the plan's own fail-closed rule (§2 Option A, constraint 4) then proceeds "exactly as today: error, FailClosed, residue marker." **Under answer (b), a correctly implemented lease produces exactly the observed failure and the §5 proof stage fails red even with S1+S2 landed.**

The observed log signature (`privileged helper connect failed (/private/var/run/rustynet/rustynetd-privileged.sock)`) is consistent with both answers — connect-refused against a removed job and connect-refused mid-deferral look identical from the dialing side. The plan must therefore resolve Q-1 from the run's stage logs *before* S1, not "before code lands" in the abstract, and must carry a fallback for answer (b): if the observed failure was helper-gone-before-restart, the primary fix must include restoring helper liveness on the daemon-restart path (adapter re-`bootstrap` of the helper job when `launchctl print system/com.rustynet.privileged-helper` fails, before `restart_daemon`), which the plan nowhere contains. Note the installer already has the exact primitive M2 needs for this: the post-bootstrap socket-wait at `Install-RustyNetMacosService.sh:614-625` ("Wait up to 10 s for the helper socket to materialise").

This is the single finding that can make the whole plan land green in tests and red in the lab.

## 2) F2 — The plan silently drops the design doc's sign-off gate and inverts its recommended priority

The design document (`MacOsHelperShutdownOrderingDesign_2026-08-27.md`) marks §2/§3 as "BLOCKED ON OWNER SIGN-OFF" (header, line 4; §3 heading, line 201: "DEFERRED — SIGN-OFF REQUIRED"), and §3.2's recommendation (line 254) is "**Option A + Option B together**, with A first (it is mechanical...)" — where the design's Option A is the *callers-wait teardown-site repair* and its Option B is the *lease*. The implementation plan (i) makes the lease primary and the teardown-site repair "explicitly NOT the production fix" hygiene (§0), inverting the design's priority without stating the inversion or its justification, and (ii) proceeds to an implementation program whose status tracker (§ "Status tracker") has rows for the refute pass and every S/M step but **no sign-off row at all**. A privileged-boundary change (new request kinds on a root helper's authenticated socket) is exactly what the design gated behind sign-off; the plan inherits the design's constraints verbatim (§2 "Constraints (non-negotiable)") but not its gate. Amendment A2 restores it.

## 3) F3 — The design's §3.3 caveat ("all of §3 may be the wrong fix") is unaddressed

Design §3.3 (`MacOsHelperShutdownOrderingDesign_2026-08-27.md:258-278`) records that the *previous* QH-40 remedy was refuted because the observed rollback failures were `truncated frame header` I/O timeouts with the helper **still alive** — not an ordering failure — and that the same failure signature appeared on `bootstrap_apply_failed` and `membership_reconcile_failed`, paths with no teardown in flight. Its conclusion: "Landing Option A/B against a failure actually caused by an I/O timeout would produce a green-looking change that fixes nothing — which is exactly how the previous QH-40 remedy got refuted."

The 2026-09-02 evidence escapes this specific trap — the recorded text is `privileged helper connect failed`, the connect-time signature (`crates/rustynetd/src/privileged_helper.rs:467`), not the read-time `truncated frame header` — so the ordering hypothesis is the right one *for this run*. But the plan never says so. It must, because §5's clean-restart proof cannot distinguish "lease fixed the race" from "the timeout mechanism did not fire this time" unless the plan (a) states that the observed signature is connect-class, not read-class, and (b) requires the §5 negative-path re-proof (forced helper death → marker) to also cover a *wedged-but-alive* helper (accepting, not reading), which is the signature §3.3 actually warns about. Amendment A3.

Relatedly: §3.3's failing non-teardown paths (`bootstrap_apply_failed`, `membership_reconcile_failed`) run rollback through the same `Phase10Controller` machinery, and the plan's S2 scopes the lease to the shutdown-signal gate "`daemon.rs:12226` region **and/or** `Phase10Controller::shutdown` (`phase10.rs:7797`)" — an ambiguity that decides coverage. If the lease is acquired only in the signal gate, error-path rollbacks remain unleased and keep racing any concurrent teardown. The lease belongs inside `Phase10Controller::shutdown` itself (or at every `rollback_generation_best_effort(CleanShutdown)` entry), not beside one caller. Amendment A4.

## 5) F5 — Lease liveness and the DoS question: the design survives, but the plan never states the holding mechanism

**What holds the lease.** Nothing in the plan says. The only coherent reading, and the one the invariants imply, is: lease state is **process memory inside the running helper** (owner peer credential + deadline), with the framed unix-socket connection as the channel. This must be stated in the plan because it answers every liveness question deterministically:

- *Daemon SIGKILL:* the kernel closes the daemon's socket fds on process death, so the helper observes EOF on the lease-owner's connection at SIGKILL time. The helper-side defer deadline (I-3) is then the sole bound, and it is ≤ 3000 ms by S/M0 — under the measured 5000 ms ceiling (`MACOS_LAUNCHD_EXIT_TIMEOUT_MS = 5_000`, `privileged_helper.rs:102`; ceiling measured, per design §8.1 `MacOsHelperShutdownOrderingDesign_2026-08-27.md:386-402`). A lease therefore cannot outlive a dead daemon by more than the defer budget, and there is **no lease file** for anyone to clean up after SIGKILL — the failure mode "stale lease file pins the helper" cannot occur in this design, but only because the lease is not a file; say so.
- *Helper death:* lease state dies with the helper process. A bootout-then-`bootstrap` respawn starts with no lease (plan §6 Q-2 is right to demand the daemon treat "lease vanished" as "helper gone").
- *Can a lease outlive a dead daemon beyond the bound?* No — but note the plan's I-1 phrasing ("never exits while a lease is unreleased, except deadline") combined with §2's "renews-for-same-peer" admits a renewal pattern that resets the defer window. Under any renewal pattern the extension is still capped: the helper can only defer *its own SIGTERM exit*, launchd escalates to SIGKILL 5 s after that SIGTERM regardless of lease state (no rustynet plist declares `ExitTimeOut` — verified by grep across `scripts/launchd/` and `scripts/bootstrap/macos/`; the only match is the design note at `Install-RustyNetMacosService.sh:54`), and SIGKILL destroys the lease with the process. So the theoretical worst case is "helper lives ~5 s longer than it otherwise would", never "indefinitely".

**DoS lever: closed.** The daemon runs unprivileged as `rustynetd` (daemon heredoc `UserName` = `rustynetd`, `Install-RustyNetMacosService.sh:491-492`); the helper heredoc declares no `UserName` and therefore runs as root. The accept loop's peer-credential gate is the only path to a lease: `peer_uid(&stream).is_some_and(|uid| uid == config.allowed_uid || uid == 0)` (`crates/rustynetd/src/privileged_helper.rs:685`, with `peer_uid` at `:3095` and the unauthorized-peer rejection response immediately following). An unprivileged local process that is neither the `rustynetd` user nor root cannot acquire, renew, or release a lease — it gets the existing unauthorized response. A lease-holder is by construction at least as privileged as the daemon itself, and the lease grants no operation the daemon does not already exercise (`validate_request` argv allowlist, `privileged_helper.rs:1886`, is unchanged; the lease adds a control-plane request kind, not an exec branch). **Block-a-legitimate-stop** is equally bounded: a lease can delay a helper's exit at most one defer budget, and "stop" under launchd is enforced by SIGKILL at the ceiling regardless. The plan's constraints section asserts these outcomes but never derives them; A5 requires the derivation in the plan so the implementer cannot accidentally move lease state to a file (which would resurrect the cleanup question) or a shared daemon-side counter (which would resurrect the spoofing question).

**Q-3 arithmetic needs one more line.** The deployed timeout pair is helper server 2000 ms / daemon client 3000 ms (`PRIVILEGED_HELPER_TIMEOUT_MS="${RUSTYNET_PRIVILEGED_HELPER_TIMEOUT_MS:-2000}"` at `Install-RustyNetMacosService.sh:62`, margin `+1000` at `:156`, ceiling check at `:160-163`; Rust constants `DEFAULT_PRIVILEGED_HELPER_TIMEOUT_MS = 2_000` at `privileged_helper.rs:79` and the daemon-side default at `daemon.rs:581`). The plan's Q-3 "pick TTL ≥ client timeout so a granted lease is never orphaned by its own acquisition call" has a residual edge it does not name: with TTL = defer = 3000 ms and client timeout 3000 ms, an acquire that *times out* client-side may still have been granted server-side (the response raced the client deadline). The daemon then rolls back unleased while the helper holds a lease it will never see released — harmless today (defer fires at the deadline), but it means "acquire timed out ⇒ no lease" is false, and the release-on-all-paths test (plan S2) must include that case or it will be skipped as impossible. Amendment A6.

## 6) F6 — Option B's deadline arithmetic is wrong as specified, and can push the daemon past its own SIGKILL mid-rollback

The daemon's own SIGTERM-to-SIGKILL budget is the same measured 5000 ms ceiling. The plan proposes "deadline 1500 ms, small backoff" at the connect site. Two defects:

1. **The deadline cannot bound an attempt it does not own.** The per-call client timeout on the rollback path is the §8.7-derived 3000 ms (`daemon.rs:581` default, passed as the helper client timeout). Against a *dead* helper, `UnixStream::connect` fails in microseconds and the retry loop is cheap; against a *wedged* (alive, accepting, not reading) helper, connect succeeds, the framed write+read burns the full 3000 ms, and a 1500 ms deadline that only wraps the connect call never fires in time. The retry wrapper must set each attempt's timeout to `min(client_timeout, remaining_deadline)` or the deadline is decorative exactly in the case it exists for.
2. **A per-site deadline stacks across multiple helper calls.** DNS rollback alone makes more than one helper round trip — the pf apply and the resolver restore via the SC helper client (`crates/rustynetd/src/macos_dns_sc_protect.rs:1473` dials the same privileged socket; the `rollback_dns_protection` route is `phase10.rs:6980-6982` → `phase10.rs:958`). Two calls × (1500 ms retry window + up to 3000 ms call) can exceed 5000 ms of daemon lifetime, and launchd's SIGKILL then lands **mid-rollback**: the DNS stage fails, later stages never run, the key scrub at `daemon.rs:11782/11790` still runs before the `ShutdownRollbackResidue` return at `:12415` (that ordering is inside the post-loop path and survives SIGKILL only if the scrub is reached — a mid-rollback SIGKILL also kills the scrub). The residue marker is written synchronously at failure time (`daemon.rs:12235-12242`), so it survives, but the rollback residue itself gets *worse* than today, not better. Fix: the deadline must be a **rollback-global budget** established once at `Phase10Controller::shutdown` entry (e.g. 1500 ms total), consumed across all helper dials in that rollback, with per-attempt timeouts derived from the remainder. Amendment A7.

For the same reason the plan's R-3 mitigation ("deadline well inside the daemon's 5 s budget") is under-specified: "well inside" of *what* — one call, or the whole rollback — is exactly the difference between the two failure shapes above.

## 7) F7 — Residue-marker invariant: confirmed intact (no refutation)

Verified, not assumed: `shutdown_residue.rs` removes the marker only via the explicit acknowledgement path (`acknowledge_marker`, `:264`; "never automatically on daemon start" comment at `:258`; the `scan`-must-not-remove mutation guard test at `:451`), renders `PolicyReject` exit 78 (`:429-434`), and matches the observed connect-failed signature in its trigger classification (`:285`, `:420`). The plan's §2 "What does NOT change" and I-2 add no clear or suppress path, S1–S3 touch only the acquire/defer/retry surfaces, and the negative-path test I-2 requires keeps the marker on lease-refusal. **Pass.** The only marker-adjacent risk found is F6's mid-rollback SIGKILL, which degrades *rollback completeness*, not marker visibility.

## 8) F8 — The plan's live evidence does not distinguish fix from luck; deterministic tests below

A single `enforce_baseline_runtime → validate_baseline_runtime` pass proves little on its own: the design measured the daemon's graceful shutdown at **1.020 s against a 1.0 s sleep** (`MacOsHelperShutdownOrderingDesign_2026-08-27.md:186-190`), i.e. the same-stop race already wins ~half the time *without any fix* when the helper is merely mid-teardown, and a clean single restart can pass by luck under answer (a) of F1 even with the lease absent or broken. The plan's §5 table (residue-marker absence on clean restarts) has the same weakness: marker absence is the *expected* state of any lucky run.

What actually distinguishes the fix is **distributional and adversarial evidence**:

1. **Unit (in-process, no launchd):** spawn the helper server on a temp socket, connect as the allowed uid, `Acquire`, then deliver a **real `SIGTERM`** (libc `kill` on the helper's thread — not a synthetic flag) and assert: the accept loop keeps serving a second authenticated request for the defer window; after `Release` (or deadline expiry) the process exits; with no lease it exits immediately. This is I-1/I-3 made deterministic.
2. **Negative (fail-closed unchanged):** with the helper job removed (`bootout`), SIGTERM the daemon and assert today's exact signature — `ShutdownRollbackResidue` returned after the key scrub, marker written, exit 78 on the check. This is the F1-answer-(b) guard: it must pass *before and after* the lease, proving the lease changes nothing about failure.
3. **Lab (the race, made deterministic by repetition):** one ssh command per trial that runs `launchctl bootout system/com.rustynet.daemon; launchctl bootout system/com.rustynet.privileged-helper` back-to-back (the exact `MACOS_LAUNCHD_STOP_COMMAND:47,49` defect pair, isolated from the anchor/relay tail), then `bootstrap` the daemon again and assert: rollback succeeded (no `shutdown_rollback_residue_detected` in the daemon log, marker absent), and `validate_baseline_runtime` is green. Run **N ≥ 20 trials**; a broken lease fails each trial with p ≈ 0.5 (design's 20 ms margin), so 20/20 has a false-green probability of ~10⁻⁶. Assert also the defer observable: while the lease is held, `launchctl print system/com.rustynet.privileged-helper` still reports the job running after the helper's SIGTERM, and the job's exit timestamp is ≥ release time and inside the 5 s ceiling — this distinguishes "lease deferred exit" from "helper respawned fast".
4. **§5 amendment:** the "Clean-restart residue check" row must require the N-trial form above (or the plan's equivalent), not a single restart, and must record the trial count in the evidence artifact — a stage row that does not state N has not run the test.

## 10) Fail-closed tests the implementation MUST write before S1 code

1. `lease_acquire_unauthorized_peer_refused` — connect as a uid that is neither `allowed_uid` nor root; assert the existing unauthorized response and that no lease state exists afterwards (I-4's enforcement is the `:685` peer gate; this is its verification).
