### The two results most worth knowing

**S2 needed a shared primitive, not four patches.** The same
presence-vs-precedence defect sat at *five* sites; a per-backend guard is the one
shape that can drift and look fixed on the platform that was audited. The core is
transport-agnostic because pf and nftables differ in syntax, not precedence
semantics. Two encoded subtleties: `Escapes` is the fail-closed default, and
nftables **prints** a chain `policy` above the rules while **applying** it below
them — a walk trusting textual order concludes at rule zero.

**PF-13's sweep earned itself immediately.** Mutating `decode` to drop the
`strict` field — a genuinely lossy decode — leaves **all four** pre-existing
round-trips passing, including the one that asserts spec equality but only at
`strict=false` where the loss is invisible. Only the new sweep fails.

## 4. Parked decisions — do not resolve these without the operator

Filed with full evidence; each needs a judgement that is not mine to make.

- **IPV-15** (High, new) — on a node that both serves as an exit and has DNS
  protection, `apply_nat_forwarding` appends the wide-open output-chain accept
  **before** `apply_dns_protection` appends the port-53 fail-closed drops. Both
  use `nft add rule` (append), both land in the same `killswitch` chain, so
  nftables takes the accept first and **plaintext DNS to a LAN/ISP resolver
  egresses freely** while the presence-based assertion reports the protection
  installed. Confirmed by reading the installers and the runtime call order.
  Reordering trades one control against another — the output-chain accept is
  arguably intended on a node that *is* the internet gateway.
- **POL-15** (Medium, new) — `selected_exit_node` is tracked separately by
  `DaemonRuntime` and `Phase10Controller`. `ExitNodeSelect` keeps them
  consistent, but state restore and auto-exit assign only the daemon's, and the
  LAN-route gate reads the controller's. Confirmed by test, not inferred.
- **POL-06 inertness** — `set_membership_directory` has **zero production
  callers**, so `is_populated()` is always false in a shipped binary and the
  RSA-0008 issuance gate never runs. Needs a CLI contract decision across
  `execute_assignment`, `execute_dns_zone_issue`, `execute_traversal_issue`.
- **RLY-17** (Low, new) — the daemon-side clock twin is fail-closed **by
  accident**: its expiry check is dead at `now = 0`, but a neighbouring
  future-dating check rejects everything. Comment fixed; hardening open.

## 5. Traps that cost real time — do not rediscover these

1. **The `u64::MAX` sentinel for RLY-15 is unsafe.** It fixes expiry and breaks
   anti-replay: `NonceStore::prune` filters on `now - inserted_at >= retention`,
   so `u64::MAX` evicts **every** nonce. `0` is the mirror. No single value is
   fail-closed for both — hence `Option` with a per-call-site disposition. The
   remediation row still offers the sentinel; it is annotated as unsafe.
2. **Windows-only code *can* be compile-verified on this Mac.** A Homebrew
   `rustc 1.97` shadows the pinned 1.88.0 (there is no `~/.cargo/bin`), which
   makes **every** cross-target build fail with a misleading
   `can't find crate for 'core'`. Use:
   ```bash
   T=~/.rustup/toolchains/1.88.0-aarch64-apple-darwin/bin
   RUSTC=$T/rustc PATH=$T:$PATH $T/cargo clippy -p rustynet-windows-native \
     --target aarch64-pc-windows-msvc --all-features --locked -- -D warnings
   ```
   This caught a dead-code warning that would have failed the Windows CI leg.
   `rustynetd` cannot be reached this way — `libsqlite3-sys` needs a Windows C
   toolchain.
3. **Two `#[test]` attributes register a test twice**, so the count goes *up*.
   A rising count after an edit that added no test is that bug.
4. **Source-pin tests self-match.** Assemble needles at runtime
   (`format!("fn write_{}", "restore_file")`), or the file always contains the
   literal and the assertion is permanently true. Two of my pins were vacuous
   until fixed. Same trap as `pkill -f` matching its own command line.
5. **Slice production code at the test *module*** (`"#[cfg(test)]\nmod tests {"`),
   not the first `#[cfg(test)]` — there are `#[cfg(test)]` attributes on
   production helpers.
6. **Duplicate finding ids.** I filed two findings under ids that already
   existed. They are now `PF-16` and `IPV-15`; commits `3b598514` and `cecb8773`
   say `PF-11` and mean `PF-16`. Check the id space before filing.

## 6. The flake, and why the fix is what it is

`vm_lab::tests::execute_ops_vm_lab_discover_local_utm_updates_inventory_ip_even_when_ssh_unreachable`
failed once inside the full workspace suite and passes in isolation in 6.6s.

Causation was settled rather than assumed: clean `HEAD` passed the full workspace,
and a re-run *with* the change also passed (exit 0, 153 binaries each). Not a
regression — a pre-existing load-sensitive flake.

Per CLAUDE.md §7 the isolated green is the misleading result, so it was fixed at
the mechanism. Two wrong turns first, both caught by measuring:

- Raising the test's timeout is **not** safe: 2s → 20s took it from **6.6s to
  55.7s**, because the SSH probe waits its full budget against a blackholed
  RFC 5737 address. The short timeout is load-bearing.
- Three sibling tests exceeding 60s is **baseline behaviour** (106s for the
  group, 2:10 wall either way), not caused by the fix.

Real defect: one `timeout_secs` knob bounds both a network probe to an
unreachable host and a local process exec, which want opposite values. Fix is a
floor on local probes only. Mutation-verified.
